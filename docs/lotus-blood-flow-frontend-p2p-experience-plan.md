# 血流玩法：前端与 P2P 的对局、表现及 AI 方案

日期：2026-09-05。状态：体验设计补充，尚未实现。可执行顺序、配置与验收以[主实施方案](lotus-blood-flow-implementation-plan.md) E00～E09 为准；本文不再维护独立阶段编号。

本文件承接 `lotus-blood-flow-implementation-plan.md` 的番型、十三幺 16 倍、硬胡 ×2 及逐分解评分规则。用户已将本轮范围明确为前端与 P2P，不实施 Python 游戏后端或 WebSocket 新玩法。下文的动画时长、摆牌容量、LLM 冷却及决策预算是首测建议。

## 1. 范围与已有能力

交付目标：同一 TypeScript 规则引擎服务单机与 P2P 房主；四个客户端显示同一批次的收付、各自胡牌楼、番型和对局状态。单机使用本机主题；P2P 沿用现有房主主题同步与客机主题锁定，不新增混主题房间。性能档位和静音可以因客户端不同而不同。

用户确认的主题与时机边界：LLM / 角色感言只在整局结束后、且观看客户端使用 `llm`（大模型专属）或 `llmAnime`（大模型二次元）主题时启用；`jade`、`happyMahjong`、`rosewood` 均无感言。对局中的胡牌事件只复用现有“胡 / 自摸”等动作报声代码和资源，不新增或替换一套报声，不触发评价、赢家感言、付款者反应或全桌感言。限制同时适用于感言文字气泡与语音，不影响规则动作音、番型展示、得分、胡牌特效或 AI / LLM 决策本身。

当前代码核对：

| 能力 | 已有基础 | 新模式需要补足 |
|---|---|---|
| 单机胡牌 | `lotusSettlement.ts` 与共享结算时间线 | 胡一次只结算一次局内事件，不触发整局亮牌 / 终局感言 |
| 3D 胡牌特效 | `components/table/three/winEffectPresenter.ts` 已有飞牌、光束、粒子、震动与缓存 | 从一个赢家改为批次多赢家，按等级与主题选表现，长局重复时压缩 |
| 五主题 | 默认墨玉、欢乐麻将、红木金丝、大模型专属、大模型二次元 | 同一事件模板用各主题的 token / 材质 / 字效，不能默认全部金光或二次元化 |
| P2P 权威 | `online/host/hostGameRunner.ts`、`localStateToSnapshot.ts` | 复用 authorityEpoch、序号、座位定向快照，增加血流批次及楼层记录 |

## 2. 参考“万能无限胡”的方式

希望借鉴的是：牌型名称明确、胡牌瞬间有力度、重复胡牌能形成可见积累，高番比普通胡牌更有表现。

公开资料入口：

- [欢乐麻将无限胡版本介绍](https://www.sohu.com/a/519479525_121124835)：文字介绍提到超多番型、连续胡牌和番型名称表现。
- [无限胡大四喜实机视频入口](https://www.bilibili.com/video/BV1y3411c7Wr/)：作为后续逐镜头参考入口。

本次检索未完成该模式实机的逐帧核对，因此下文具体时长、镜头、音效和堆叠算法均是本项目提案，不声称是竞品实测参数。也不把红中血流、无限换牌血流或其他名字相近玩法混作同一模式。

效果制作前补一轮短参考验收：普通胡、牌型大胡、同人连续大胡、一炮多响、胡牌楼超过一层。分析信息出现顺序、遮挡范围和重复演出的压缩方式；本项目资源自行制作，使用已有主题概念。

“莲花”仍只表示地名与规则来源。不使用花瓣、荷叶、莲花印章或由地名推导的地域画面；九莲宝灯也优先用牌型字效和牌面组合表现，不把名称扩展为项目级花卉符号。

## 3. 一次胡牌的完整处理

### 规则与表现分离

1. 房主创建本次响应窗口，固定来源牌、候选玩家、截止时间和状态版本。
2. 收齐胡 / 过。多位玩家同胡是同一个批次，不能按谁先发消息就只收一个赢家。
3. 房主统一验牌，计算每位赢家的最佳合法分解、硬胡、倍率及四家收付；实体源牌只归档一次。
4. 原子提交账本、胡牌记录、次数、锁手状态；发出 `win_batch` 公共事实及各座位私有快照。
5. 客户端按该批次调度字效、分数、胡牌张飞入与楼层变化。
6. 房主按规则设定下一个动作窗口。短暂表现节拍可以统一由房主安排，但不等待每台机器动画播完或 TTS 播完。

首测统一留约 450ms 的局内胡牌节拍；宏大效果可以在席位附近继续收尾。下一动作真正开放时才启动其倒计时。设备弱、静音、标签页后台不会改变谁摸牌，也不能缩短其他人的合法响应时间。

### 队列必须有边界

- 同时最多一个中央大标题；每个席位可有一个局部胡牌反馈。
- 普通重复反馈建议 350～500ms，较完整的大番演出控制在 1.2～1.6 秒。
- 同一席位同一主番首次出现完整播放；之后局部缩短，冷却建议 8 秒。换成更高等级番型时可以升级。
- 一炮多响只安排一个公共片头，赢家的席位卡同时出现或轻微错峰；不要三人各播一次全屏动画。
- 消息积压时压缩 / 合并过期视觉队列，直接恢复所有楼层与分数；账本及胡牌记录不丢，不要求把 20 次历史特效补播完。
- 动画生成、开始或结束都不能产生扣分、发牌、锁手等规则副作用。

## 4. 牌型怎么显示，特效怎么分级

### 每次胡牌都显示实际计分依据

席位短卡显示：主番名称、可叠加的其他番型、硬胡 / 自摸等修饰、本次最终倍率与本人收支。非基本牌型不能只显示一个“胡”字。

例如：

> 清一色 · 碰碰胡　硬胡 ×2 · 自摸 ×2　20 倍　+600

该例基础组合为 5 倍，底分 10，三家各付 200，赢家共收 600。主标题最多一个主番、副标题最多两项，其余显示“另 N 项”，在本局流水中展开完整详情。被包含而未加分的项不冒充计分番型。

不要把最终倍率、基础番型倍率、单家支付和赢家总收益混成同一个数字。封顶时显示“封顶 64 倍”，原始组合及封顶前倍率放详情。

### 四级表现建议

等级主要由最终选中的计分分解中的最高基础番型档位决定；硬胡、自摸增加徽标、声效层次和亮度，不让普通平胡只凭硬胡自摸就套用顶级稀有番型演出。

| 等级 | 触发 | 首次表现建议 | 同牌型重复胡 |
|---|---|---|---|
| 普通 | 平胡、2 倍基础番 | 清楚动作字、短高光、分数跳动、飞牌落层 | 短字效和落层声，约 350～500ms |
| 中番 | 4 倍基础番 | 牌型标题放大、两段节奏、主题化轨迹 | 保留牌型短卡，压缩轨迹 |
| 大番 | 8 倍基础番 | 更明显的入场、局部背景强调、受控粒子与组合标签 | 局部爆发，避免重复遮桌 |
| 顶级 | 16 倍基础番 | 约 1.2～1.6 秒完整演出、强调牌型名和胡牌张，主题允许时角色短切入 | 紧凑版大番演出，记录次数仍逐次增长 |

达到封顶增加独立的“封顶”强调，不改变牌型真实性。基础组合很高但没有单个 16 倍番型时，可给组合倍率增加大番强调，不能伪造一个不存在的顶级番型名称。

五主题共享动画轨道，视觉来源分别是：

- `jade`：实体牌落地、克制的高光与清晰字效。
- `happyMahjong`：明快圆润的标题、弹性节奏、层次更丰富的色彩。
- `rosewood`：温暖材质、金属边缘反光、稳重的落牌与音色。
- `llm`：既有星轨 / 数据主题的轨迹和倍率信息。
- `llmAnime`：既有漫画字效、角色框与短切入，不让固定桌布人物冒充获胜玩家。

音效优先使用预制可缓存资源，番型文字在前端绘制。低画质 / reduced-motion 模式移除震屏、闪白及高成本粒子，但保留番型、分数、胡牌张和楼层结果。

## 5. 四家“盖楼”怎么做

### 一家一个独立胡牌区

- 胡牌区与暗手、副露、普通牌河分离，靠本家席位的侧方空白区；按四个座位旋转本地坐标，牌面应可辨读。
- 每次胡牌在对应玩家的展示楼增加一张“胡牌记录牌”，显示真实胡牌牌面，不显示精牌被解释成的虚拟牌面。精牌代替了什么在有权限的详情中解释。
- 首测桌面摆法：每层 4 张，每楼最多 3 层，共 12 张可见记录；超过 12 张时分段收纳旧记录，保留最近 12 张及“已胡 N 次”。移动端可压缩为每层 3 张、2 层。
- 楼只长在预留区域，不无限增高，不遮挡暗手牌、其他人的牌河、操作按钮或待牌提示。容量按视口和主题布局配置，不写入玩法规则。
- 新牌沿来源位置飞入，落到目标记录槽轻弹；整层完成有短提示，不给分数加倍。继续积累只改变视觉与次数。
- 点击胡牌楼打开该玩家的本局公开流水：第几次、胡什么牌、主番、修饰、谁付款及净分。默认不展示其尚未公开的完整暗手牌或精牌分配。

### 多响与实体牌必须分开

一张弃牌被三家胡时，三个胡牌楼都增加一张展示记录，引用同一个 `sourceTileEventId`。实体牌库只移除 / 归档一张；显示三次不意味着生成了三张牌。

待牌剩余张数和公开牌计数必须从实体归档账读取，不得从楼里绘制的 mesh 数量统计。多响共用一张来源牌；重复收到网络事件不重复盖楼。

示例：A 打四筒，B / C / D 均胡。A 的来源牌归档一次，B / C / D 分别有一条胡牌记录和一次楼层增长；A 一次性扣除三笔应付总和。下一摸牌者按既定续行规则确定，不能由最后播完动画的玩家决定。

### 重连与容量

楼层数据由 `winsBySeat` / 事件序号重建，动画只是增量表现。重连时立即恢复楼的当前外观和总次数，不从第一个胡牌事件开始逐张飞牌。完整本局流水保留到局末，本局结束后才清空楼并进入下一局。

开发验收至少覆盖四家各 0、1、4、12、40、80 条记录的布局压力，以及一炮三响。高数量是 UI 压力数据，不代表单局一定能产生该分布。

## 6. 普通 AI 怎么改

### 三种决策阶段

1. 首胡前：比较成牌速度、可见剩余听牌张数、当前收益、大牌潜力、硬胡机会和放炮风险；不能只按番型最大或一味最快胡。
2. 首次可胡：明确比较“现在胡并锁手的预期后续收益”与“过胡继续做牌的预期收益和风险”。硬胡 ×2、宽听口和剩余墙长都影响这次选择。
3. 首胡后：在锁手方案下，不再运行完整弃牌搜索；能胡按策略胡，否则只打新摸牌。除用户选择的自动胡 / 过规则外，不再生成吃碰杠候选。

收益评估使用公开信息。即便房主引擎拥有全牌墙与四家暗手，也必须先构造座位视图再交给 AI；不能把后端 / 房主的全局状态直接拿去算最优弃牌。

设进攻、稳健两类基准策略，用同样随机种子对比早点胡与追大牌。长期目标不是让 AI 都追求十三幺，而是让番型目标随实际手牌改变。先把稳定的规则 AI 做好，它也是所有 LLM 超时或错误时的兜底。

完整评分在纯 TypeScript 模块实现，耗时的分解与 AI 前瞻适合移到 Web Worker；返回带状态版本，过期结果不用。Worker 是同源前端运行时，不是新增游戏后端。

## 7. LLM 决策怎么调用

### 合法性由前端权威引擎负责

- 扩展 `schema.ts`、`candidates.ts`、`prompt.ts`、`llmController.ts`，为新模式提供真实可选择的胡、过、出牌、吃碰杠候选。
- 首胡前取消“只要能胡就直接 return win”的新模式短路；是否立即胡成为一个有候选特征的策略决策。
- 不把规则计算交给模型。每个候选由引擎提供可核对的当前倍率、硬胡可行性、自摸 / 点炮听口、可见剩余张数、结构变化、是否锁手等。
- 让模型选候选 ID，并允许附带一句短话；不接受模型自报番数、修改牌或任意动作。
- 返回后按 `authorityEpoch + roundId + actionWindowId + requestId` 核对当前状态及合法性。过期、非法、超时均调用规则 AI。

### 调用预算

默认走“关键决策调用”策略：无分支的强制摸打不调用；有价值取舍的弃牌、吃碰、首胡 / 过胡才调用。局内胡牌不请求独立感言，即使决策返回了自由评价，也只保留经过确认的简短动作报声；不能为了保持话痨而每次胡牌再发起请求。

首测普通决策网络预算约 2～3 秒，关键首胡 / 过胡约 4～5 秒，始终小于本次权威动作截止时间并预留兜底执行时间。它们是本模式建议，保留现有明确用户设置的优先级，不能以节奏优化为由偷偷覆盖用户已配置的超时偏好。

房主对房间 AI 发起一次请求，其他客户端只消费结果，不各自为同一个 AI 请求模型。并发上限建议 2；多响响应中的多个模型共用同一窗口截止时间，不能顺序等待每家完整超时。

网络队列延迟也算在预算内；语义重试只能使用剩余预算。首胡后强制动作由确定性策略处理，主要节省点来自少调用，而不是把所有模型请求都设置极短超时。

### 前端与外部服务的边界

不实施 Python 游戏后端，不代表禁止使用现有 LLM 服务。复用浏览器已有的模型预置、平台授权或兼容的直连服务；API Key 留在配置它的客户端，不进入 P2P 包。

已有 TTS 网关可以继续作为可选增强，但不新增接口、不依赖其可用性来完成对局。没有兼容的 LLM 连接则规则 AI 继续；没有 TTS 则预制动作音 / 字幕继续，不为此新增代理后端。

## 8. LLM 发言频率与声音怎么控制

先检查整局是否已结束，再按观看客户端的当前主题判断感言能力。只有局末的 `llm` / `llmAnime` 可以进入感言通道；局内胡牌或其他三个主题在排队和 TTS 请求之前就丢弃感言，不只是把声音静音。这里整局结束指牌墙耗尽并完成本局结算，不是某个人首次胡牌；不必等整场 4 / 8 局全部结束。

分成三条通道，各自有职责：

| 通道 | 内容 | 频率 / 队列建议 |
|---|---|---|
| 规则动作音 | 现有胡、自摸、碰、杠及落牌声音 | 复用现有代码、音频及角色路由，不重写台词；新批次接线确保不双播，不请求 LLM 自由评价 |
| 番型播报 | 清一色、十三幺、硬胡、封顶等 | 每次文字必有，音频仅主番；同席同番重复 8 秒内不重复长播报 |
| LLM / 角色感言 | 整局结束后的角色化反应或一句评价，仅 `llm` / `llmAnime` | 本局结算去重、按席位有序播放、可跳过的短队列 |

用户已撤回此前局内“全桌 6 秒 / 单席 12～30 秒冷却、首次胡或逆转触发、赢家加付款者反应”的方案，改为以下规则：

- 对局中的首次胡、顶级番型、封顶、重复胡、胡牌次数里程碑、排名逆转及一炮多响，均不触发感言。
- 局内胡牌仍有番型卡、倍率、分数、特效、盖楼及简短动作报声。角色音色及措辞沿用当前配置，不在本轮重写；此前“我胡了”只是举例，不是新增录音或台词需求。
- 普通出牌 / 吃碰杠的已有动作反馈与 LLM 决策照常处理，不把“取消胡牌感言”误实现为关闭打牌决策或全部声音。
- 整局结束后再根据本局净分、胡牌次数和已公开的大牌安排全桌感言。有配置感言的席位每席最多一句，建议本局净分第一名先说，其余按固定座位顺序，避免同时抢话。
- 局末感言绑定唯一局结果 ID，重连 / 重复结算不重播整套。局末使用短的可跳过队列，不沿用局内 6 秒间隔逐人等待。
- 进入下一局、返回大厅或切到非 LLM 主题时取消未完成感言；迟到模型 / TTS 回调不得在新局补播。
- important / mandatory 不能绕过“仅局末”的准入限制。局内胡牌不发起自由感言生成请求。

P2P 由房主在整局结算后依据公共结果生成感言，客户端先核对本局已结束，再按本机主题判断是否接收表现，再按静音和音频可用性播放同一 `speechEventId`。沿用已有房主主题同步与锁定，以本机已生效的房间主题做准入防护，不新增主题偏好广播；非 LLM 主题客户端不显示感言气泡、不请求或播放感言 TTS，也不等待其完成。房间主题不支持感言时跳过独立感言生成请求。不要让四台客户端分别生成不同台词；也不要让同一台机器同时播放其自己生成和收到广播的两份语音。

从 LLM 相关主题切到其他主题时，立即清空待播感言、隐藏其气泡并取消本机正在播放或请求中的感言；迟到回调需复核主题版本，不能重新出现。切回 LLM 主题只接收后续新感言，不补播之前被屏蔽的历史。此切换不取消有效的 LLM 打牌决策，也不更换 AI 控制器。

感言采用广播后的公共事实输入，不传暗手牌或内部决策推理。动作发言可沿用现有过滤器；结算反应需单独允许已经公开的真实番型名称，否则当前对“清一色”等词的私牌过滤可能把合法播报也替换掉。规则音和计分文字必须来自结构化结果，不能让模型编造。

新模式局内语音不等待 P2P midpoint barrier；广播发言只是表现事件，不推进或阻塞规则。局末仍可有短的展示窗口，但不等待四家云端 TTS 无限串行完成。

## 9. P2P 的一致性和失联边界

- 单一房主运行 TypeScript 权威引擎，其他玩家发送动作意图。计分、胡牌归档和场次推进都由房主提交。
- 复用现有 authorityEpoch 与消息序号，补充规则版本、局 ID、批次 ID、响应窗口 ID；动作去重和表现去重分别处理。
- `win_batch` 是可补发的局内事实；`round_settled` 只在墙耗尽等真正局末发送；新胡牌不能触发 `serializeRevealedPlayers` 的整桌亮牌。
- 公共快照含四家分数、胡牌楼摘要、已公开的番型、锁手状态；每人私有快照仅含其自己的手牌和合法操作，不公开牌墙顺序。
- 收到比分新快照时不能再应用旧批次增量。维护已提交事件序号，缺号时请求补齐或权威快照。
- 普通玩家重连后恢复分数、锁手、胡牌楼、当前响应窗口，不重播全部历史特效和感言；恢复期间不立即把短暂 P2P / Relay 切换当成永久离席。
- 房主暂时失联时客户端暂停新动作并尝试恢复原权威。首版不凭公共快照擅自选新房主续打，因为公共快照不含完整暗手和牌墙。
- 若房主浏览器永久退出且无可恢复权威状态，保留最后确认的流水，提示对局中断；不伪造正常完局战绩。完整无缝房主迁移是额外能力，不在首版承诺内。
- 前端房主架构不能保证房主本人绝对无法查看其浏览器内的全局状态；复用现有洗牌承诺与公开验证，但不将其宣传为等同独立服务端裁判的防作弊能力。

## 1. 已冻结的产品决策

### 1.1 “莲花”只表示地方与玩法来源

项目名称中的“莲花”指地方、县城及当地麻将玩法来源，不表示花卉，也不是视觉母题。

必须遵守：

- “莲花广麻”“莲花麻将”只用于玩法、规则、规则说明和相关业务标识。
- 不从“莲花”二字推导项目 Logo、页面样式、主题、桌布、牌墙、牌背、牌河、皮肤、粒子、徽章、动作字或结算表现。
- 不新增莲花、荷花、荷叶、花瓣、莲花奖牌、莲花印章、莲花绽放等项目级视觉符号。
- 不构造“莲华首席”“莲花数据城”等由名称派生的世界观。
- 不因玩法名称推导岭南、粤式茶楼或其他未经产品决策确认的地域视觉。
- 五个主题的视觉来源必须是各自的主题概念，不能来自“莲花”地名。

`llmAnime` 当前桌布若含普通花卉图案，只能视为该二次元主题自身的装饰语言，不代表莲花县，不代表规则，也不建立玩家身份关系。除非另有明确需求，本轮不以“清除所有普通花卉”为目标。

### 1.2 删除“雀魂风”主题

删除独立的“雀魂风”主题及运行时主题 ID `majsoul`。后续只保留五个主题：

| 主题 ID | 显示名 | 核心定位 |
|---|---|---|
| `jade` | 默认墨玉 | 经典、稳重、精致的实体麻将桌 |
| `happyMahjong` | 欢乐麻将 | 明快、圆润、有节奏的休闲对局 |
| `rosewood` | 红木金丝 | 温暖、传统、有实体材质感的牌桌 |
| `llm` | 大模型专属 | 星轨、数据与模型对抗 |
| `llmAnime` | 大模型二次元 | 角色群像、漫画字效与动作演出 |

删除主题时必须完成：

- 从主题注册表、选择器、类型定义和 URL 合法值中删除 `majsoul`。
- 删除 `majsoulTheme` 及仅由它使用的配置和运行时资源。
- 历史 URL `?theme=majsoul` 必须安全回退到 `jade`，不得白屏或抛出未处理异常。
- 本地偏好中保存的 `majsoul` 必须迁移或回退到 `jade`。
- 更新主题选择、偏好解析、资源缓存、视觉矩阵和相关测试。
- 活跃文档、用户界面和代码注释不再把竞品名称当作本项目主题名称。
- `llmAnime` 的材质说明改用“低写实商业 3D”“圆角树脂牌体”“软阴影”“偏长焦机位”等中性技术描述。
- 通用木框、蓝色材质、圆角牌体和软阴影能力如果仍被其他主题使用，应保留；不得因为删除主题而误删共享渲染能力。
- 历史测试证据可以保留，但必须明确属于已废弃主题，不得继续进入主动回归矩阵。

### 1.3 角色身份与桌布装饰分离

- 玩家身份由玩家框、头像、昵称、分数、状态、动作卡和语音表示。
- 桌布上的固定人物或图案属于主题装饰，不与四个座位一一绑定。
- `llmAnime` 固定群像不因玩家更换本家形象而更换整张桌布。
- 主题装饰不得承载权威玩家状态，也不得使玩家误认为装饰人物就是对应座位玩家。
- 如果装饰人物靠近座位，需通过底纹、构图、透明度或整体连贯关系表达其“桌布群像”属性。

## 2. 改造目标

本轮目标不是把所有主题二次元化，而是把“只换台面颜色和牌背”的材质主题升级为完整的表现主题。

最终每个主题需要同时覆盖：

1. 大厅氛围；
2. 主题选择预览；
3. 牌桌环境与 3D 材质；
4. 顶栏和玩家席位；
5. 加载、开局、回合与动作提示；
6. 吃、碰、杠、胡等事件表现；
7. 单局结算与最终结算；
8. 移动横屏、竖屏门禁、错误和重连状态。

### 2.1 成功标准

- 遮住牌桌中央后，仅看外围 HUD、玩家框、动作提示和结算，仍能辨认当前主题。
- 常态对局保持清楚、稳定；关键事件具有明显但不过度的情绪幅度。
- 五个主题共享业务组件和布局骨架，不复制五套页面。
- 主题差异来自表现 token、有限变体和资源，不进入规则引擎或联机协议。
- 任一主题资源失败时仍可完成对局。
- `llmAnime` 已有桌布群像和角色演出不因共享改造回退。

## 3. 范围与非目标

### 3.1 本轮范围

#### 大厅

- 页面环境背景与主题氛围层；
- Logo、副标题及主要信息层级；
- 登录区域；
- 单机/联机模式卡；
- 场次与玩法设置；
- 本家形象入口；
- 开始按钮；
- 主题选择器；
- 声音、规则和 AI 设置入口；
- 创建/加入房间及等待状态；
- 登录、房间和资源错误状态。

#### 对局

- 页面环境背景；
- 牌桌、桌框、中控台、牌面和牌背；
- 顶部局况 HUD；
- 四家玩家框、庄家、风位和分数；
- 当前玩家和倒计时；
- 手牌选择、可打提示和摸牌位；
- 吃碰杠胡、过、托管等操作区；
- 吃/杠多选面板；
- 听牌、翻精和癞子提示；
- LLM 气泡与状态；
- 开局、普通动作、胡牌和分数变化；
- 加载、重试、断线、重连和等待其他玩家。

#### 结束流程

- 亮牌；
- 流局；
- 自摸、点炮和抢杠胡；
- 单局结算；
- 最终排名；
- 查看牌桌、下一局、返回大厅和举报入口；
- 固定角色赛后语音等待期间的表现。

#### 系统状态

- 竖屏提示与全屏横屏入口；
- 键盘焦点、悬停、按下、禁用和加载状态；
- 静音与 `prefers-reduced-motion`；
- 图片加载失败和 WebGL 初始化失败；
- 手机、平板、桌面、矮窗和超宽屏。

### 3.2 非目标

- 不修改麻将规则、计分、AI 决策和联机权威状态。
- 不改变牌墙、牌河、手牌和操作区的核心玩法几何。
- 不要求五个主题使用角色立绘。
- 不把主题状态同步为房间权威数据；主题仍是客户端表现偏好。
- 不在本轮新增角色养成、抽卡、商城或付费系统。
- 不以模仿任一竞品作为主题验收标准。

## 4. 现状判断与优先级

| 主题 | 已有优势 | 主要缺口 | 优先级 |
|---|---|---|---|
| `jade` | 结构稳定、经典墨绿金色 | 单色、外围 HUD 与加载态缺少仪式感 | P1 |
| `happyMahjong` | 青绿绒面清楚 | 台面、背景与牌背过于接近，工具感最强 | P0 试点 |
| `rosewood` | 暖色方向明确 | 红桌与绿色牌背冲突，材质和外围表现较空 | P1 |
| `llm` | 星轨桌布已形成场景 | 绿色牌背、通用 HUD 与星轨语言不统一 | P1 |
| `llmAnime` | 固定群像、桌布和动作演出最完整 | 大厅、角色选择、通用横幅和结算未完全跟上 | P1 |

## 5. 主题表现架构

### 5.1 现有边界

- `TableTheme` 继续负责 Three.js 几何、材质、桌布、牌体、牌背和灯光参数。
- 新增 `ThemePresentation`（最终命名可按项目习惯调整）负责 DOM/UI、环境、动作和结算表现。
- `App.vue` 现有 `data-table-theme` 继续作为 CSS 主题作用域。
- `GameTableHud`、`PlayerSeat`、开局提示、动作 cue 和结算组件保持共享。

### 5.2 建议合同

```ts
interface ThemePresentation {
  identity: {
    label: string
    description: string
    previewUrl: string
    colorScheme: 'dark' | 'light'
  }
  shell: {
    pageBackground: string
    ambientOverlay?: string
    motif?: string
    particle?: 'none' | 'dust' | 'stars' | 'confetti' | 'theme-art'
  }
  palette: {
    surface: string
    panel: string
    panelElevated: string
    text: string
    textMuted: string
    border: string
    accent: string
    accentSecondary: string
    positive: string
    negative: string
  }
  typography: {
    headingClass: string
    numberClass: string
    actionClass: string
  }
  hud: {
    playerFrame: 'jade' | 'playful' | 'wood' | 'cosmic' | 'anime'
    topBar: string
    button: string
    tooltip: string
  }
  presentation: {
    loading: string
    opening: string
    action: string
    win: string
    settlement: string
    error: string
  }
  motion: {
    ambient: string
    activeSeat: string
    actionEnter: string
    scoreChange: string
  }
}
```

### 5.3 合同约束

- 每个保留主题必须有完整配置；不得依赖隐式散落的主题判断。
- 非必填视觉资源必须定义默认回退。
- 未知主题、旧 `majsoul` 和损坏的本地偏好统一回退 `jade`。
- 主题切换后不得残留上一主题的 DOM class、CSS 变量、纹理或动画。
- 主题资源 URL 必须使用统一构建方式并兼容 `BASE_URL`。
- 新视觉差异不得写入规则、动作合法性或联机协议分支。
- 布局坐标继续由共享响应式变量控制，主题不得重新引入设备枚举式几何覆盖。

## 6. 共享组件改造规格

### 6.1 大厅

- 保留统一信息架构，不复制五套大厅。
- 页面环境背景、面板材质、按钮强调色和主题预览随主题变化。
- 场次、玩法和账号仍保持易扫描；不能为追求氛围牺牲设置可读性。
- 主题选择器由纯文字长列表升级为带缩略图、名称和一句描述的主题卡。
- 主题选择器不得出现突兀的原生白色滚动条；滚动条需要主题化或改为无需滚动的响应式布局。
- `llmAnime` 才显示本家形象入口；其他主题不显示无效角色入口。
- 页面视觉不得使用从“莲花”地名推导的花卉或地域装饰。

### 6.2 顶部 HUD

- 统一组织场次、局数、剩余牌数、底分和功能入口。
- 桌面端形成视觉相关的一条 HUD；移动端可以拆分，但层级一致。
- 主题改变容器、边框、强调色和轻动效，不改变数据语义。
- 规则、声音和主题按钮需要与当前主题一致，不能长期保留统一墨绿金色外观。

### 6.3 玩家席位

- 头像、昵称、分数、庄家、风位和状态组成一个完整席位组件。
- 当前行动玩家必须有清楚但不刺眼的主题化高亮。
- 分数变化在席位附近显示，并与最终分数状态一致。
- 离线、重连、托管、思考和等待状态使用可辨识徽章。
- 玩家席位不得遮挡牌墙、牌河、手牌、翻精提示和操作按钮。
- 桌布固定装饰不参与席位身份计算。

### 6.4 加载与错误

- “牌桌资源加载中”不得继续固定使用单一墨绿遮罩。
- 每个主题至少改变背景色、边框、加载指示和强调色。
- 资源失败需提供明确重试按钮和文本，不能只靠颜色表达。
- WebGL 失败时使用轻量 DOM 回退，保证错误信息可读。

### 6.5 开局提示

- 时间线、文案和无障碍文本共享；外框和运动语言按主题变化。
- 开局提示不得遮挡关键操作，也不得与主题装饰产生身份混淆。
- reduced-motion 使用无位移淡入版本。

### 6.6 动作与分数变化

| 事件 | 强度 | 建议时长 | 要求 |
|---|---:|---:|---|
| 当前玩家切换 | 轻 | 180–300ms | 席位高亮，不遮牌 |
| 摸牌/出牌 | 轻 | 120–240ms | 不阻塞输入 |
| 分数变化 | 中 | 500–800ms | 席位附近展示，最终值一致 |
| 吃/碰 | 中 | 500–750ms | 从动作玩家方向进入 |
| 杠 | 中强 | 650–900ms | 强于吃碰，弱于胡牌 |
| 听牌 | 中 | 500–800ms | 不泄漏隐藏信息 |
| 开局 | 强 | 900–1500ms | 沿用权威开局流程 |
| 胡/自摸 | 高潮 | 沿用现有结算时间线 | 可参与既有表现屏障 |
| 最终排名 | 高潮 | 1200–2000ms | 不阻塞退出与返回大厅 |

- 普通动作动画不得延迟权威动作提交。
- 除现有胡牌/固定语音合同外，主题动画不得成为业务屏障。
- 移动端降低粒子、模糊和阴影成本。
- reduced-motion 禁止大位移、强缩放冲击和循环粒子。

### 6.7 结算

- 保留统一算分数据结构和操作按钮。
- 主题决定容器、标题、排名卡、分数动画和背景表现。
- 首要信息顺序固定为：结果类型、赢家/流局、分数变化、牌型明细、排名、后续操作。
- 举报、返回、查看牌桌等功能不得因主题皮肤弱化或丢失。

## 7. 五主题规格卡

### 7.1 默认墨玉 `jade`

**定位**：经典、稳重、精致的实体麻将桌。

**视觉来源**：深色玉石、硬质结构、克制金属和材质高光；不使用花卉、地名或地域符号。

- 深绿保持主色，但增加表面层次和局部高光，避免整屏同一暗度。
- 玩家席位使用深色硬质框和细金属边，当前席位通过玉石流光或亮度变化表达。
- 开局使用几何玉牌或印鉴式构图，但印鉴不得使用莲花图案。
- 吃碰杠使用墨迹、切面光或金属冲击线。
- 结算采用清晰的牌局账板，不使用莲花、荷叶或地名装饰。
- 环境保持安静，但关键动作必须有足够对比和声音反馈。

### 7.2 欢乐麻将 `happyMahjong`

**定位**：明快、圆润、有节奏的休闲对局。

**视觉来源**：高明度色块、几何图形、圆润按钮、弹性动画和节庆纸屑；不绑定具体地域。

- 拉开青绿桌面、环境背景和牌背之间的明度与色相差。
- 增加暖黄作为主要行动色，可使用少量橙红作为高潮强调。
- 玩家席位和操作按钮使用圆润、厚实、易点击的块面。
- 开局与普通动作使用短促弹跳和几何爆发。
- 胡牌可使用彩带、纸屑和奖牌台，但禁止金币雨、赌场筹码和持续闪烁。
- 作为 `ThemePresentation` 的首个试点主题，先验证共享合同再推广。

### 7.3 红木金丝 `rosewood`

**定位**：温暖、传统、有真实材质感的牌桌。

**视觉来源**：红木、漆面、黄铜、暖光和纸张；不绑定具体地方文化。

- 增加可感知但不过度的木纹和漆面层次。
- 调整当前绿色牌背；优先评估奶油/暗红、深色漆面或与红木协调的配色。
- 玩家席位使用木框、黄铜角件和暖白文字。
- 当前席位通过暖光和金属反射强调。
- 动作使用朱色印记、纸张或切面冲击；不得使用由“莲花”名称派生的印记。
- 结算使用传统牌局账单或卷轴式信息结构，但保持现代可读性。

### 7.4 大模型专属 `llm`

**定位**：星轨、数据与模型对抗。

**视觉来源**：深蓝星轨、数据线、全息信息、推理状态和能量反馈。

- 保留现有星轨桌布和双模型装饰。
- 调整绿色牌背与星轨场景的冲突；优先评估蓝紫、深蓝或带数据纹样的牌背。
- 玩家席位、顶栏和加载态改为深蓝全息框，不再沿用墨绿金色。
- 推理、等待和发言状态通过安全的状态环或数据脉冲表达，不展示原始推理。
- 开局和动作使用扫描、能量线和数据切换。
- 结算可增加简短模型战报，但不得变成调试面板，也不得暴露内部推理。

### 7.5 大模型二次元 `llmAnime`

**定位**：角色群像、漫画字效、固定语音和动作演出。

**视觉来源**：现有角色美术、幻想色彩、漫画构图和主题自身的装饰语言。

- 保留现有固定群像桌布；群像不与玩家座位身份绑定。
- 暂不继续放大或增加桌布人物，优先改造外围 UI。
- 大厅强化当前本家形象的预览，但玩法设置仍需清楚。
- 角色选择器升级为大预览、完整名称、角色说明、选中反馈和可选语音试听入口。
- 开局、加载、气泡和结算统一为二次元表现，减少通用墨绿金色面板的割裂。
- 玩家本家形象只影响对应头像、动作卡、强调色和语音，不触发整张桌布更换。
- 普通花卉若保留，只是本主题装饰，不解释为项目名或玩法来源。

#### 一套视觉语言、两种表面颜色

`llmAnime` 不再混用“奶油漫画风”“墨玉深绿控件”和“通用金色按钮”三套语言。主题冻结为一套二次元漫画视觉，只保留两种主要表面颜色：

| 表面 | 建议基准色 | 职责 |
|---|---|---|
| 深色场景层 | 深鼠尾草黑，基于现有 `#18231e` / `#29372f` | 页面背景、常驻大厅操作区、联机房间、顶栏、牌桌 HUD、大模型配置抽屉 |
| 奶油纸张层 | 基于现有 `#fff8ec` / `#f3e5cf` | 场次/玩法/角色选择、创建/加入确认、漫画气泡、临时选择卡和重要信息 |

珊瑚红 `#bd5b48`（深色文字变体可使用 `#9f4035`）只承担功能强调：当前选中、确认、当前状态和关键动作。青蓝 `#78d8e8` 只作为少量辅助信息和角色效果色。金色 `#c7a45b` 不再承担普通确认按钮，只保留在分数、特殊结果、极少量边缘细节或仪式性信息中。

统一规则：

- 深色和浅色不是两个主题，而是同一主题中的“场景层”和“纸张层”。
- 深色区域使用奶油白正文；奶油纸张区域使用墨色 `#2d2923` 正文。
- 两种表面共享同一套墨色描边、圆角范围、珊瑚选中标记、轻微错位阴影和主次按钮层级。
- 场次、玩法、角色、创建和加入弹窗的外壳与内部选项必须全部属于奶油纸张层，不能在奶油弹窗中出现墨玉深绿或灰绿色大块选项。
- 奶油纸张层的普通选项使用奶油/次奶油底与弱墨色边框；选中项使用浅珊瑚底、珊瑚边或左侧强调线和明确勾选。
- 奶油纸张层的主按钮使用珊瑚红，次按钮使用奶油底与墨色边；不使用通用金色“确定”按钮。
- 深色常驻区域可以使用奶油色文字和珊瑚状态，但不得把完整奶油弹窗样式复制到所有大面积常驻面板。
- 大模型配置抽屉属于深色场景层，其字段和卡片使用同主题表面与珊瑚选中态；配置内容和行为保持不变。
- 任一组件不能同时出现奶油漫画外壳、墨玉深绿选项和通用金色主按钮。

## 8. 资源规范

每个主题原则上控制在以下新增资源范围：

- 1 张大厅或环境背景；
- 1 张桌面叠加纹理或现有桌布复用；
- 1 张主题预览缩略图；
- 1 套可复用装饰纹样；
- 1 套动作背景；
- 1 套结算框；
- 可选的轻量粒子贴图。

每项资源必须记录文件路径、来源和授权、源文件与生成步骤、宽高和格式、字节数、响应式裁切、加载策略及失败回退。

约束：

- 非 `llmAnime` 不得加载其角色动作资源。
- 主题缩略图应轻量并可随大厅首屏加载。
- 大图必须提供适当的压缩运行时版本。
- 不使用未经确认的竞品资源、Logo、角色或直接复制的 UI 图形。

## 10. 响应式、可访问性与性能

- 沿用现有共享响应式骨架，不为五个主题复制坐标。
- 主要触控目标不小于 44×44 CSS px。
- 文字、图标和状态不能只靠颜色区分。
- 焦点样式必须可见并随主题保持足够对比。
- 主题装饰不得遮挡浮层、玩家状态、手牌、牌河和操作区。
- 验证 568×320 至 3840×2160，以及现有手机、平板、桌面和随机临界尺寸矩阵；其中竖屏视口只验收横屏门禁，不验收门禁后的大厅或牌桌。
- 主题切换不得泄漏纹理、材质、定时器或音频任务。
- 大厅不得预加载五套完整动作和结算资源。
- 低性能配置降低粒子、阴影、模糊和环境动画成本。
- reduced-motion 关闭循环粒子、强位移和冲击缩放，但保留状态反馈。
- 资源失败时回退共享 UI，不影响规则和操作。

#### Phase 8：大厅布局增量改造

##### 目标

##### 桌面与横屏

- 使用统一的“双区域”信息结构：普通桌面默认左侧为主题视觉区，右侧为对局操作区；只有极端宽高比或现有响应式约束确有需要时才允许调整方向。
- 主题视觉区负责展示当前主题的牌桌、环境或本家形象；不承载规则设置和权威玩家状态。
- 对局操作区保留账号、单机/联机、场次、玩法和开始按钮，按一个连续任务流排列。
- 登录属于次级功能，不占据首要视觉焦点。
- 主 CTA 按当前任务状态确定：单机大厅为“开始对局”；联机未入房为“创建房间”和“加入房间”；创建/加入弹窗为“确认”；已入房普通玩家为“准备/取消准备”；房主在全员准备后为“开始对局”。模式、场次和玩法必须在当前主操作附近形成清楚的配置摘要。
- 同一状态下只突出当前可执行的主操作；禁用的“开始对局”不得与仍可执行的“准备”等操作争夺视觉焦点。
- 不是强制 50:50 双栏，可根据现有连续响应式变量采用非对称比例；不得新增按具体设备宽度枚举的布局分支。

- 开发服务器下的视觉验收必须等待当前可见预览图片真实完成加载后再截图；以图片 `complete && naturalWidth > 0` 或等价的页面 ready 状态为准，不用固定等待时间冒充资源已就绪。

##### 降低大厅工具感

大厅去工具感依靠信息层级和视觉构图，不依靠增加更多边框、面板或说明文字。

- 主题视觉区应作为大厅主视觉的一部分，不再表现为“外层容器里再放一张设置卡”的多层套框。
- 角色或牌桌预览可以通过留白、背景光、局部越框或弱底板建立焦点；不要求所有内容拥有同等粗细的描边。
- 对局操作区最多保留一个主要承载面板；内部模式、设置和账号使用分组、间距与明度建立层级，避免每一层都成为独立卡片。
- 模式切换可以保留分段按钮，但场次和玩法优先使用分隔线而不是再次套入完整内层卡片；账号区域改为低权重底栏，不与开始按钮争夺视觉层级。
- 同一信息原则上只完整出现一次。开始按钮已经包含当前场次与玩法时，删除完全重复的“当前配置”整行；只有存在开始前必须确认且按钮副标题无法表达的信息时，才允许保留紧凑摘要。
- 单机大厅以开始按钮为高权重操作；联机流程按未入房、确认弹窗、已入房和房主可开局状态切换当前高权重操作。模式切换和设置保持中权重，登录、规则、战绩和仓库链接保持低权重。
- 不显示面向开发或解释内部实现的说明文字。桌布固定群像与玩家身份分离属于产品合同和测试要求，不在大厅可见正文或无障碍名称中显示“与四名牌手身份无关”等开发说明。

**共享结构下的主题差异：**

- 五个主题继续复用同一大厅组件和左右结构，不制作五套独立页面。
- `jade` 使用实体材质特写、硬边和克制高光，避免表现为绿色线框模板。
- `happyMahjong` 使用明快全幅画面、圆润边缘和较活泼的色彩关系，避免只替换背景色。
- `rosewood` 使用暖光、可感知木纹和窄金属边，避免只显示棕色矩形。
- `llm` 让星轨和双模型画面成为连续场景，避免在多层边框内缩成普通缩略图。
- `llmAnime` 以当前角色为视觉焦点，允许角色图局部越框；不继续增加桌布人物或把桌布群像映射为玩家。
- 这些差异通过图片裁切、背景、边框强弱和现有主题变量实现，不新增另一套大厅组件体系。

**主题与本家形象文案必须分离：**

- 非 `llmAnime`：显示“当前牌桌主题”与主题名称。
- `llmAnime`：角色主视觉显示“当前本家形象”与角色名称，不得显示成“当前牌桌主题：角色名称”。
- `llmAnime` 的牌桌主题另以低权重信息表示为“牌桌主题 · 大模型二次元”。
- 角色名称在主视觉标题区只显示一次；原本重复角色名称的操作行简化为“更换本家形象”。
- 欢迎文字服务于角色氛围，不重复角色名称，也不重复“当前牌桌主题”“本家形象”等字段标签。例如标题已显示“智谱狐姬”时，欢迎文字只写“准备好一起开局了吗？”。

##### 移动横屏与竖屏门禁

- 手机和平板只在横屏门禁放行后展示实际大厅；移动横屏允许压缩或裁切主题视觉区，操作区必须保持完整可读。
- 窄横屏可以使用更紧凑的双区域或上下分区，但不能只是把桌面窄列等比缩小。
- 竖屏不展示、测试或维护实际大厅布局，只显示项目既有的“请横屏游玩”门禁和全屏横屏入口。
- 自动化不得通过隐藏门禁、修改样式或直接调用内部状态来假测竖屏大厅；必须先通过真实旋转/横屏条件，再验收实际移动大厅。
- 弹窗、主题菜单和角色选择器打开后不得造成主页面横向跳动或操作区错位。

##### 移动横屏联机状态布局

移动横屏必须区分“尚未进入房间”和“已经进入房间”两种任务状态，不能始终保留同一套桌面双栏。

**尚未进入房间：**

- 保留紧凑的主题视觉区与操作区，视觉区原则上不超过可用宽度的约三分之一。
- 主题视觉区合并品牌、预览和主题名称，避免标题、大片空白和预览卡彼此分离。
- 操作区优先展示单机/联机切换、昵称、服务器状态和创建/加入按钮。
- 账号、战绩、规则和仓库链接属于次级入口；空间不足时应压缩或收纳，不得挤压创建/加入操作。
- 移动横屏字号、说明文案和卡片高度需使用紧凑规格，不能直接沿用桌面尺寸。

**已经进入房间：**

- 切换为“房间聚焦模式”，房间面板占据主要可用宽高。
- 移动横屏隐藏完整主题视觉区，最多保留一个紧凑主题徽章或主题名称。
- 房间码、场次/玩法、房间时限、四个座位和准备/开始操作构成房间主内容。
- 账号、GitHub、战绩等非当前任务内容应隐藏、收纳或移出主内容区。
- `llmAnime` 本家形象在房间内只显示紧凑入口，点击后打开既有弹窗；不得把完整角色选择器直接内嵌到移动房间面板中。
- 标准手机横屏下，四个座位与准备/开始操作必须无需滚动即可看到。

##### 大厅滚动合同

- `html`、`body`、`.game-app`、`.lobby` 和大厅根布局不得产生纵向或横向页面滚动。
- `.lobby` 不得以 `overflow-y: auto` 作为内容超高时的通用兜底；`overscroll-behavior` 也不能代替禁止根容器滚动。
- 大厅根布局必须受当前可用视口高度约束，并为 grid/flex 子项设置正确的 `min-height: 0`。
- 主题菜单、声音菜单和模态弹窗可以在自身边界内滚动，但不得带动整个大厅移动。
- 844×390、800×360、667×375 等标准手机横屏应通过布局压缩在一屏内完成主要任务，不依赖内部滚动。
- 568×320 等极端横屏若确实无法容纳全部房间信息，只允许房间中间内容区内部滚动；准备、开始、离开等关键操作必须保持可见或固定在房间面板底部。
- 在页面非滚动区域上下拖动时，大厅根容器的位置必须保持不变。

##### `llmAnime` 大厅补充

- 显示当前本家名称和一句不重复角色名的短欢迎文字；首版只显示文字，不自动播放欢迎语音。
- 角色列表不要求永久铺在大厅底部；可继续通过本家形象入口打开选择器。
- 大图、欢迎文字和选择入口不得暗示桌布群像就是四名玩家。
- 正式 UI 的可见文本和无障碍名称均不显示“桌布群像为固定主题插画，与四名牌手身份无关”等开发说明；该约束只保留在文档和测试中。

#### Phase 9：共享外围表现收口

在现有主题系统上补齐浏览器复核仍显通用或工具化的外围组件：

- 顶部 HUD；
- 玩家席位；
- 牌桌加载层；
- 开局横幅；
- 吃、碰、杠、胡、过和托管操作按钮；
- 吃/杠候选面板；
- 听牌与规则提示；
- 单局结算和最终结算。

约束：

- 使用现有主题 CSS 变量与事件表现映射，不新增另一套表现 registry。
- 主要、次要、危险、禁用、加载和键盘焦点状态必须可区分。
- 常态牌局保持安静；只在开局、鸣牌、胡牌和分数变化时提高表现强度。
- 不以新增大量粒子或延长动画作为“去工具化”的主要手段。
- 结算只调整面板内部进入顺序和视觉层级，不改变既有“胡牌表现 → 亮牌/固定语音 → settled”合同。
- 从“查看牌桌”返回结算时直接恢复稳定最终状态，不重复播放整段进入动画。

##### 前端主题一致性审计范围

Phase 9 不能只检查大厅主卡、牌桌和结算。以下用户可见表面均属于五主题视觉统一范围：

| 表面 | 必须随主题变化 | 不得随视觉改造改变 |
|---|---|---|
| 大厅模式区 | 面板、按钮、选中态、焦点态、禁用态 | 单机/联机含义与切换行为 |
| 场次摘要与选择器 | 弹窗、选项、单选标记、确认/取消按钮 | 东风场/半庄场名称、局数与确认逻辑 |
| 玩法摘要与选择器 | 弹窗、选项、徽章、说明层级、查看规则入口 | 玩法名称、规则亮点、选择与确认逻辑 |
| 创建/加入房间 | 输入框、主次按钮、状态文字层级 | 昵称、房间码、创建/加入请求与校验 |
| 已加入房间 | 房间码、配置摘要、座位卡、准备/开始/离开/关闭按钮 | 房间状态、座位、准备和开局逻辑 |
| 主题菜单 | 预览卡、选中态、滚动条和失败占位 | 五主题集合、切换和持久化行为 |
| 声音菜单 | 容器、开关、选中和禁用状态 | 音效/BGM/语音开关含义 |
| 大模型配置页 | 面板、字段、供应商卡、按钮、状态和滚动条 | 全部配置项、顺序、默认值、校验、保存和测试行为 |
| 规则面板 | 容器、标题、分隔线、按钮和滚动条 | 规则正文和声明内容 |
| 战绩面板 | 容器、统计卡、正负分和关闭按钮 | 统计值、加载和空状态逻辑 |
| 竖屏门禁 | 背景、卡片和按钮 | 必须横屏的产品规则 |
| 牌桌 HUD/弹层 | 玩家框、提示、操作按钮和选择面板 | 游戏状态、可执行动作和时序 |
| 单局/最终结算 | 容器、排名卡、主次按钮和动画 | 算分、排名、查看牌桌和继续逻辑 |

- 审计时应优先查找写死的墨绿、金色、固定字体、固定边框和固定阴影；能够表达主题语义的值改用现有主题变量。
- 五主题不要求所有组件形状完全不同，但同一主题内的面板、按钮、输入、选中态和焦点态必须使用同一视觉语言。
- 视觉改造不得顺手重排业务字段、删减说明、重命名配置项或改变默认行为；内容改动必须另立需求。

##### Teleport 弹层的主题上下文

`LobbyDialog` 和 `LlmSettingsPanel` 使用 `Teleport to="body"`，不能依赖 `.game-app[data-table-theme="..."] .lobby-dialog` 一类祖先选择器继承主题。

- Teleport 到 `body` 的组件必须显式获得当前主题名或完整主题 CSS 变量，并在弹层根节点设置稳定的 `data-table-theme`/主题 class。
- 弹层应复用现有 `ThemePresentation` 变量，不复制五套硬编码样式。
- 切换主题时，已打开的弹层必须同步更新，不要求关闭后重新打开。
- 弹层关闭后不得在 `body` 留下主题 class、滚动锁或内联变量。
- 不把主题状态写入场次、玩法、大模型配置或其他业务数据。

##### 房间码与房间头部

- 房间码在房间面板顶部水平居中，恢复其作为房间主识别信息的视觉位置。
- “房间码”标签、实际六码和复制成功反馈构成一个居中的整体；复制反馈出现或消失不得推动房间码偏移。
- 场次与玩法摘要位于房间码下方并保持居中，层级低于房间码。
- 房间码区域保持可点击和键盘可操作，点击复制、Enter 复制及“已复制”反馈行为不变。
- 桌面和标准移动横屏都必须居中；极端窄横屏可以缩小字距和字号，但不得回退为左对齐。
- 房间时限、座位、准备状态、开始/离开/关闭按钮继续使用既有内容和逻辑，只调整视觉和布局。

##### 场次选择与玩法选择

- `LobbyDialog`、`MatchTypePicker`、`RuleVariantPicker` 作为一套共享选择体验统一换肤。
- 弹窗容器、标题、关闭按钮、选项卡、单选标记、说明文字、徽章、查看规则、取消和确定按钮必须读取当前主题。
- 每个主题均需覆盖默认、悬停、按下、选中、键盘焦点和禁用状态，不能只有 `llm`/`llmAnime` 有额外样式而其他主题沿用墨玉硬编码。
- 场次选项继续只包含当前业务定义的场次；不改变名称、局数说明、临时选择和确认后生效的行为。
- 玩法选项继续使用 `RULE_VARIANTS` 的名称、徽章和规则亮点；不改文案来源、不隐藏规则差异。
- 玩法说明在移动横屏下允许换行，不能因主题样式产生不可辨识省略；弹窗内容超高时只滚动弹窗内容，不滚动大厅。
- “查看详细规则”保持低于选项、高于取消/确定的辅助层级，不能被主题样式弱化到不可发现。

##### 大厅按钮与表单控件

大厅按钮统一按语义角色换肤，不再由各组件分别使用互不相干的固定颜色：

| 角色 | 对应操作 |
|---|---|
| 主操作 | 开始单机、创建房间、加入房间、确认创建、确认加入、房主开始对局 |
| 次操作 | 模式切换、场次/玩法入口、准备/取消准备、登录 |
| 轻操作 | 查看规则、战绩、GitHub、复制房间码、返回/关闭 |
| 危险操作 | 离开房间、关闭房间、删除供应商、清除 Key |

- 同一语义角色在五主题中保持一致权重，但颜色、圆角、描边和阴影随主题变化。
- 主操作不能与普通选项卡或账号登录拥有相同视觉权重。
- 危险操作不能只通过文字颜色区分，必须有稳定的危险态语义；同时不得误做成页面主 CTA。
- 文本框、密码框、下拉框、复选框、单选标记和滚动条都必须使用主题表面、文字、边框、强调色和焦点色。
- 输入值、placeholder、错误、成功、禁用和只读状态必须清楚；主题换肤不得降低 API Key 等敏感字段的遮蔽和浏览器自动填充约束。
- 主题只改变表现，不改变按钮事件、disabled 条件、表单校验、键盘提交和异步状态。

##### 大模型配置页：只换主题，不改内容

`LlmSettingsPanel` 的本轮范围严格限定为视觉主题适配。

必须保持不变：

- “启用”开关；
- 供应商列表、当前供应商和默认供应商语义；
- 模板选择与添加；
- 三个座位的模型和风格分配；
- 名称、昵称、头像文件夹、供应商协议、Base URL、API Key、模型、超时、风格和单机音色字段；
- 中转/始终思考警告；
- 删除供应商、保存、测试连接、清除 Key、导入和导出；
- 导入导出说明、保存/测试状态、本局统计和消息列表；
- 字段顺序、默认值、持久化格式、安全约定、测试请求与开局生效时机。

允许改变：

- 抽屉背景、边框、阴影和滚动条；
- 标题、正文、弱文字、警告、成功和失败的主题颜色；
- 输入框、下拉框、复选框、供应商卡和座位分配区的表面样式；
- 默认/当前供应商的选中态；
- 主、次、危险、禁用和加载按钮样式；
- 焦点环、间距和不改变字段顺序的响应式尺寸。

实施约束：

- `LlmSettingsPanel` 不得继续写死为墨绿金色；五主题打开时必须读取对应主题变量。
- 由于面板 Teleport 到 `body`，必须显式注入主题上下文，不能依赖 `.game-app` 祖先。
- 面板继续在自身内部滚动，打开或滚动时不得带动大厅；关闭后恢复原页面滚动状态。
- 不借视觉统一之名精简、折叠、重命名或重新组织配置内容。

#### Phase 10：`llmAnime` 轻量补齐

##### 角色选择器

- 提供一个清楚的大预览区，并显示完整角色名、简短角色说明和选中状态。
- 桌面与移动横屏默认采用“固定角色预览区 + 角色卡片区”的双区域结构；预览区保持可见，只有卡片区在内容超出时内部滚动。
- 不采用“大预览横跨整行、全部角色卡堆在其下方并被视口裁切”的长页面结构。
- 卡片区根据可用宽度使用紧凑网格；列数由容器决定，不通过具体设备型号枚举。
- 每张卡只承担“角色缩略图 + 完整角色名 + 选中状态”。角色描述集中显示在固定预览区，不在每张卡重复。
- 角色名默认完整显示，允许最多两行换行；不能用省略号截断到无法区分角色。
- 未选卡使用弱边框或弱底色，当前选中卡使用主题强调色、明确勾选和轻微层级提升；不得让所有卡片都使用同等粗重的深色描边。
- 当前角色同时出现在大预览和卡片列表是允许的：大预览用于了解角色，列表卡用于定位和切换，两者职责必须清楚。
- “选择后即时保存”属于实现说明，可删除或改为低权重的“点击切换”；不能成为弹窗视觉焦点。
- 弹窗标题、关闭按钮和固定预览区不随卡片列表滚动；滚动手势不能带动弹窗外的大厅。
- 支持可选语音试听时，必须提供明确的播放/停止状态；试听不是本阶段完成的硬依赖。
- 图片或试听失败时回退现有头像与文字，不能阻塞选择和保存。
- 选择是否即时保存沿用当前偏好行为，不新增确认步骤。

##### 轻量角色表现

首版只覆盖四类，不建立完整多表情状态机：

1. 待机：现有头像/立绘默认可以完全静态；只有现有素材与性能允许时才增加低频轻动效，静态状态也视为合格；
2. 思考：沿用现有安全状态和气泡，不展示原始推理；
3. 吃碰杠：复用现有 `call` 动作卡；
4. 胡牌/结算：复用现有 `win` 动作卡和既有固定语音。

附加约束：

- 没有专属素材时使用现有头像、边光、轻微缩放或文字 cue 回退。
- 不新增“被碰、放铳、失败、流局”专属图片作为本阶段硬要求。
- 轻量表现不得阻塞出牌、操作按钮或权威牌局状态。
- 切局、退出和主题切换时复用现有清理机制，不新建第二套动画调度器。

##### 二次元 UI 收口

- 开局、加载、气泡、操作按钮、候选面板和结算使用同一套二次元插画语言。
- “与主题一致”只指 `llmAnime` 自身的角色与插画语言，不从“莲花”地名推导花卉设计。
- 暂不继续放大或增加桌布人物，优先解决外围组件割裂。

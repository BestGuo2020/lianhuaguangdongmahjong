# 牌桌主题表现系统改造实施方案

> 状态：待实施
>
> 决策日期：2026-09-04
>
> 适用分支：先在 `master` 实施并提交，再按仓库工作流同步到 `vibehub`
>
> 本文是后续牌桌主题、外围 HUD、大厅和结算视觉改造的主规范。`docs/llm-anime-theme-implementation-plan.md` 继续保留 `llmAnime` 已完成工作的历史记录，但与本文冲突的未来视觉要求以本文为准。

## 1. 已冻结的产品决策

### 1.1 “莲花”只表示地方与玩法来源

项目名称中的“莲花”指地方、县城及当地麻将玩法来源，不表示花卉，也不是视觉母题。

必须遵守：

- “莲花广麻”“莲花麻将”只用于玩法、规则、规则说明和相关业务标识。
- 不从“莲花”二字推导项目 Logo、页面样式、主题、桌布、牌墙、牌背、牌河、皮肤、粒子、徽章、动作字或结算表现。
- 不新增莲花、荷花、荷叶、花瓣、莲花奖牌、莲花印章、莲花绽放等项目级视觉符号。
- 不构造“莲华首席”“莲花数据城”等由名称派生的世界观。
- 不因玩法名称推导岭南、粤式茶楼或其他未经产品决策确认的地域视觉。
- 五个主题的视觉来源必须是各自的主题概念，不能来自“莲花”地名。

`llmAnime` 当前桌布若含普通花卉图案，只能视为该二次元主题自身的装饰语言，不代表莲花县，不代表规则，也不建立玩家身份关系。除非另有明确需求，本轮不以“清除所有普通花卉”为目标。

### 1.2 删除“雀魂风”主题

删除独立的“雀魂风”主题及运行时主题 ID `majsoul`。后续只保留五个主题：

| 主题 ID | 显示名 | 核心定位 |
|---|---|---|
| `jade` | 默认墨玉 | 经典、稳重、精致的实体麻将桌 |
| `happyMahjong` | 欢乐麻将 | 明快、圆润、有节奏的休闲对局 |
| `rosewood` | 红木金丝 | 温暖、传统、有实体材质感的牌桌 |
| `llm` | 大模型专属 | 星轨、数据与模型对抗 |
| `llmAnime` | 大模型二次元 | 角色群像、漫画字效与动作演出 |

删除主题时必须完成：

- 从主题注册表、选择器、类型定义和 URL 合法值中删除 `majsoul`。
- 删除 `majsoulTheme` 及仅由它使用的配置和运行时资源。
- 历史 URL `?theme=majsoul` 必须安全回退到 `jade`，不得白屏或抛出未处理异常。
- 本地偏好中保存的 `majsoul` 必须迁移或回退到 `jade`。
- 更新主题选择、偏好解析、资源缓存、视觉矩阵和相关测试。
- 活跃文档、用户界面和代码注释不再把竞品名称当作本项目主题名称。
- `llmAnime` 的材质说明改用“低写实商业 3D”“圆角树脂牌体”“软阴影”“偏长焦机位”等中性技术描述。
- 通用木框、蓝色材质、圆角牌体和软阴影能力如果仍被其他主题使用，应保留；不得因为删除主题而误删共享渲染能力。
- 历史测试证据可以保留，但必须明确属于已废弃主题，不得继续进入主动回归矩阵。

### 1.3 角色身份与桌布装饰分离

- 玩家身份由玩家框、头像、昵称、分数、状态、动作卡和语音表示。
- 桌布上的固定人物或图案属于主题装饰，不与四个座位一一绑定。
- `llmAnime` 固定群像不因玩家更换本家形象而更换整张桌布。
- 主题装饰不得承载权威玩家状态，也不得使玩家误认为装饰人物就是对应座位玩家。
- 如果装饰人物靠近座位，需通过底纹、构图、透明度或整体连贯关系表达其“桌布群像”属性。

## 2. 改造目标

本轮目标不是把所有主题二次元化，而是把“只换台面颜色和牌背”的材质主题升级为完整的表现主题。

最终每个主题需要同时覆盖：

1. 大厅氛围；
2. 主题选择预览；
3. 牌桌环境与 3D 材质；
4. 顶栏和玩家席位；
5. 加载、开局、回合与动作提示；
6. 吃、碰、杠、胡等事件表现；
7. 单局结算与最终结算；
8. 移动端、横屏门禁、错误和重连状态。

### 2.1 成功标准

- 遮住牌桌中央后，仅看外围 HUD、玩家框、动作提示和结算，仍能辨认当前主题。
- 常态对局保持清楚、稳定；关键事件具有明显但不过度的情绪幅度。
- 五个主题共享业务组件和布局骨架，不复制五套页面。
- 主题差异来自表现 token、有限变体和资源，不进入规则引擎或联机协议。
- 任一主题资源失败时仍可完成对局。
- `llmAnime` 已有桌布群像和角色演出不因共享改造回退。

## 3. 范围与非目标

### 3.1 本轮范围

#### 大厅

- 页面环境背景与主题氛围层；
- Logo、副标题及主要信息层级；
- 登录区域；
- 单机/联机模式卡；
- 场次与玩法设置；
- 本家形象入口；
- 开始按钮；
- 主题选择器；
- 声音、规则和 AI 设置入口；
- 创建/加入房间及等待状态；
- 登录、房间和资源错误状态。

#### 对局

- 页面环境背景；
- 牌桌、桌框、中控台、牌面和牌背；
- 顶部局况 HUD；
- 四家玩家框、庄家、风位和分数；
- 当前玩家和倒计时；
- 手牌选择、可打提示和摸牌位；
- 吃碰杠胡、过、托管等操作区；
- 吃/杠多选面板；
- 听牌、翻精和癞子提示；
- LLM 气泡与状态；
- 开局、普通动作、胡牌和分数变化；
- 加载、重试、断线、重连和等待其他玩家。

#### 结束流程

- 亮牌；
- 流局；
- 自摸、点炮和抢杠胡；
- 单局结算；
- 最终排名；
- 查看牌桌、下一局、返回大厅和举报入口；
- 固定角色赛后语音等待期间的表现。

#### 系统状态

- 竖屏提示与全屏横屏入口；
- 键盘焦点、悬停、按下、禁用和加载状态；
- 静音与 `prefers-reduced-motion`；
- 图片加载失败和 WebGL 初始化失败；
- 手机、平板、桌面、矮窗和超宽屏。

### 3.2 非目标

- 不修改麻将规则、计分、AI 决策和联机权威状态。
- 不改变牌墙、牌河、手牌和操作区的核心玩法几何。
- 不要求五个主题使用角色立绘。
- 不把主题状态同步为房间权威数据；主题仍是客户端表现偏好。
- 不在本轮新增角色养成、抽卡、商城或付费系统。
- 不以模仿任一竞品作为主题验收标准。

## 4. 现状判断与优先级

| 主题 | 已有优势 | 主要缺口 | 优先级 |
|---|---|---|---|
| `jade` | 结构稳定、经典墨绿金色 | 单色、外围 HUD 与加载态缺少仪式感 | P1 |
| `happyMahjong` | 青绿绒面清楚 | 台面、背景与牌背过于接近，工具感最强 | P0 试点 |
| `rosewood` | 暖色方向明确 | 红桌与绿色牌背冲突，材质和外围表现较空 | P1 |
| `llm` | 星轨桌布已形成场景 | 绿色牌背、通用 HUD 与星轨语言不统一 | P1 |
| `llmAnime` | 固定群像、桌布和动作演出最完整 | 大厅、角色选择、通用横幅和结算未完全跟上 | P1 |

## 5. 主题表现架构

### 5.1 现有边界

- `TableTheme` 继续负责 Three.js 几何、材质、桌布、牌体、牌背和灯光参数。
- 新增 `ThemePresentation`（最终命名可按项目习惯调整）负责 DOM/UI、环境、动作和结算表现。
- `App.vue` 现有 `data-table-theme` 继续作为 CSS 主题作用域。
- `GameTableHud`、`PlayerSeat`、开局提示、动作 cue 和结算组件保持共享。

### 5.2 建议合同

```ts
interface ThemePresentation {
  identity: {
    label: string
    description: string
    previewUrl: string
    colorScheme: 'dark' | 'light'
  }
  shell: {
    pageBackground: string
    ambientOverlay?: string
    motif?: string
    particle?: 'none' | 'dust' | 'stars' | 'confetti' | 'theme-art'
  }
  palette: {
    surface: string
    panel: string
    panelElevated: string
    text: string
    textMuted: string
    border: string
    accent: string
    accentSecondary: string
    positive: string
    negative: string
  }
  typography: {
    headingClass: string
    numberClass: string
    actionClass: string
  }
  hud: {
    playerFrame: 'jade' | 'playful' | 'wood' | 'cosmic' | 'anime'
    topBar: string
    button: string
    tooltip: string
  }
  presentation: {
    loading: string
    opening: string
    action: string
    win: string
    settlement: string
    error: string
  }
  motion: {
    ambient: string
    activeSeat: string
    actionEnter: string
    scoreChange: string
  }
}
```

### 5.3 合同约束

- 每个保留主题必须有完整配置；不得依赖隐式散落的主题判断。
- 非必填视觉资源必须定义默认回退。
- 未知主题、旧 `majsoul` 和损坏的本地偏好统一回退 `jade`。
- 主题切换后不得残留上一主题的 DOM class、CSS 变量、纹理或动画。
- 主题资源 URL 必须使用统一构建方式并兼容 `BASE_URL`。
- 新视觉差异不得写入规则、动作合法性或联机协议分支。
- 布局坐标继续由共享响应式变量控制，主题不得重新引入设备枚举式几何覆盖。

## 6. 共享组件改造规格

### 6.1 大厅

- 保留统一信息架构，不复制五套大厅。
- 页面环境背景、面板材质、按钮强调色和主题预览随主题变化。
- 场次、玩法和账号仍保持易扫描；不能为追求氛围牺牲设置可读性。
- 主题选择器由纯文字长列表升级为带缩略图、名称和一句描述的主题卡。
- 主题选择器不得出现突兀的原生白色滚动条；滚动条需要主题化或改为无需滚动的响应式布局。
- `llmAnime` 才显示本家形象入口；其他主题不显示无效角色入口。
- 页面视觉不得使用从“莲花”地名推导的花卉或地域装饰。

### 6.2 顶部 HUD

- 统一组织场次、局数、剩余牌数、底分和功能入口。
- 桌面端形成视觉相关的一条 HUD；移动端可以拆分，但层级一致。
- 主题改变容器、边框、强调色和轻动效，不改变数据语义。
- 规则、声音和主题按钮需要与当前主题一致，不能长期保留统一墨绿金色外观。

### 6.3 玩家席位

- 头像、昵称、分数、庄家、风位和状态组成一个完整席位组件。
- 当前行动玩家必须有清楚但不刺眼的主题化高亮。
- 分数变化在席位附近显示，并与最终分数状态一致。
- 离线、重连、托管、思考和等待状态使用可辨识徽章。
- 玩家席位不得遮挡牌墙、牌河、手牌、翻精提示和操作按钮。
- 桌布固定装饰不参与席位身份计算。

### 6.4 加载与错误

- “牌桌资源加载中”不得继续固定使用单一墨绿遮罩。
- 每个主题至少改变背景色、边框、加载指示和强调色。
- 资源失败需提供明确重试按钮和文本，不能只靠颜色表达。
- WebGL 失败时使用轻量 DOM 回退，保证错误信息可读。

### 6.5 开局提示

- 时间线、文案和无障碍文本共享；外框和运动语言按主题变化。
- 开局提示不得遮挡关键操作，也不得与主题装饰产生身份混淆。
- reduced-motion 使用无位移淡入版本。

### 6.6 动作与分数变化

| 事件 | 强度 | 建议时长 | 要求 |
|---|---:|---:|---|
| 当前玩家切换 | 轻 | 180–300ms | 席位高亮，不遮牌 |
| 摸牌/出牌 | 轻 | 120–240ms | 不阻塞输入 |
| 分数变化 | 中 | 500–800ms | 席位附近展示，最终值一致 |
| 吃/碰 | 中 | 500–750ms | 从动作玩家方向进入 |
| 杠 | 中强 | 650–900ms | 强于吃碰，弱于胡牌 |
| 听牌 | 中 | 500–800ms | 不泄漏隐藏信息 |
| 开局 | 强 | 900–1500ms | 沿用权威开局流程 |
| 胡/自摸 | 高潮 | 沿用现有结算时间线 | 可参与既有表现屏障 |
| 最终排名 | 高潮 | 1200–2000ms | 不阻塞退出与返回大厅 |

- 普通动作动画不得延迟权威动作提交。
- 除现有胡牌/固定语音合同外，主题动画不得成为业务屏障。
- 移动端降低粒子、模糊和阴影成本。
- reduced-motion 禁止大位移、强缩放冲击和循环粒子。

### 6.7 结算

- 保留统一算分数据结构和操作按钮。
- 主题决定容器、标题、排名卡、分数动画和背景表现。
- 首要信息顺序固定为：结果类型、赢家/流局、分数变化、牌型明细、排名、后续操作。
- 举报、返回、查看牌桌等功能不得因主题皮肤弱化或丢失。

## 7. 五主题规格卡

### 7.1 默认墨玉 `jade`

**定位**：经典、稳重、精致的实体麻将桌。

**视觉来源**：深色玉石、硬质结构、克制金属和材质高光；不使用花卉、地名或地域符号。

- 深绿保持主色，但增加表面层次和局部高光，避免整屏同一暗度。
- 玩家席位使用深色硬质框和细金属边，当前席位通过玉石流光或亮度变化表达。
- 开局使用几何玉牌或印鉴式构图，但印鉴不得使用莲花图案。
- 吃碰杠使用墨迹、切面光或金属冲击线。
- 结算采用清晰的牌局账板，不使用莲花、荷叶或地名装饰。
- 环境保持安静，但关键动作必须有足够对比和声音反馈。

### 7.2 欢乐麻将 `happyMahjong`

**定位**：明快、圆润、有节奏的休闲对局。

**视觉来源**：高明度色块、几何图形、圆润按钮、弹性动画和节庆纸屑；不绑定具体地域。

- 拉开青绿桌面、环境背景和牌背之间的明度与色相差。
- 增加暖黄作为主要行动色，可使用少量橙红作为高潮强调。
- 玩家席位和操作按钮使用圆润、厚实、易点击的块面。
- 开局与普通动作使用短促弹跳和几何爆发。
- 胡牌可使用彩带、纸屑和奖牌台，但禁止金币雨、赌场筹码和持续闪烁。
- 作为 `ThemePresentation` 的首个试点主题，先验证共享合同再推广。

### 7.3 红木金丝 `rosewood`

**定位**：温暖、传统、有真实材质感的牌桌。

**视觉来源**：红木、漆面、黄铜、暖光和纸张；不绑定具体地方文化。

- 增加可感知但不过度的木纹和漆面层次。
- 调整当前绿色牌背；优先评估奶油/暗红、深色漆面或与红木协调的配色。
- 玩家席位使用木框、黄铜角件和暖白文字。
- 当前席位通过暖光和金属反射强调。
- 动作使用朱色印记、纸张或切面冲击；不得使用由“莲花”名称派生的印记。
- 结算使用传统牌局账单或卷轴式信息结构，但保持现代可读性。

### 7.4 大模型专属 `llm`

**定位**：星轨、数据与模型对抗。

**视觉来源**：深蓝星轨、数据线、全息信息、推理状态和能量反馈。

- 保留现有星轨桌布和双模型装饰。
- 调整绿色牌背与星轨场景的冲突；优先评估蓝紫、深蓝或带数据纹样的牌背。
- 玩家席位、顶栏和加载态改为深蓝全息框，不再沿用墨绿金色。
- 推理、等待和发言状态通过安全的状态环或数据脉冲表达，不展示原始推理。
- 开局和动作使用扫描、能量线和数据切换。
- 结算可增加简短模型战报，但不得变成调试面板，也不得暴露内部推理。

### 7.5 大模型二次元 `llmAnime`

**定位**：角色群像、漫画字效、固定语音和动作演出。

**视觉来源**：现有角色美术、幻想色彩、漫画构图和主题自身的装饰语言。

- 保留现有固定群像桌布；群像不与玩家座位身份绑定。
- 暂不继续放大或增加桌布人物，优先改造外围 UI。
- 大厅强化当前本家形象的预览，但玩法设置仍需清楚。
- 角色选择器升级为大预览、完整名称、角色说明、选中反馈和可选语音试听入口。
- 开局、加载、气泡和结算统一为二次元表现，减少通用墨绿金色面板的割裂。
- 玩家本家形象只影响对应头像、动作卡、强调色和语音，不触发整张桌布更换。
- 普通花卉若保留，只是本主题装饰，不解释为项目名或玩法来源。

## 8. 资源规范

每个主题原则上控制在以下新增资源范围：

- 1 张大厅或环境背景；
- 1 张桌面叠加纹理或现有桌布复用；
- 1 张主题预览缩略图；
- 1 套可复用装饰纹样；
- 1 套动作背景；
- 1 套结算框；
- 可选的轻量粒子贴图。

每项资源必须记录文件路径、来源和授权、源文件与生成步骤、宽高和格式、字节数、响应式裁切、加载策略及失败回退。

约束：

- 非 `llmAnime` 不得加载其角色动作资源。
- 主题缩略图应轻量并可随大厅首屏加载。
- 大图必须提供适当的压缩运行时版本。
- 不使用未经确认的竞品资源、Logo、角色或直接复制的 UI 图形。

## 9. 状态覆盖矩阵

## 10. 响应式、可访问性与性能

- 沿用现有共享响应式骨架，不为五个主题复制坐标。
- 主要触控目标不小于 44×44 CSS px。
- 文字、图标和状态不能只靠颜色区分。
- 焦点样式必须可见并随主题保持足够对比。
- 主题装饰不得遮挡浮层、玩家状态、手牌、牌河和操作区。
- 验证 568×320 至 3840×2160，以及现有手机、平板、桌面和随机临界尺寸矩阵。
- 主题切换不得泄漏纹理、材质、定时器或音频任务。
- 大厅不得预加载五套完整动作和结算资源。
- 低性能配置降低粒子、阴影、模糊和环境动画成本。
- reduced-motion 关闭循环粒子、强位移和冲击缩放，但保留状态反馈。
- 资源失败时回退共享 UI，不影响规则和操作。

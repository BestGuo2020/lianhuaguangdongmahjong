## 3. 此前东一结束无法正常进入东二的原因

已经定位并修复的主要问题不是麻将规则推进，而是结算阶段的 P2P 恢复与同步竞态：

1. 房主到客户端的通道可能处于“SDK 仍显示 open，但业务消息已经不达”的半开状态。
   客户端因此可能错过 `settled`，房主确认后仍在等待客户端，下一局无法开始。
2. 重进过程中，迟到的 `rejoin_ok` 曾无条件清空客户端已经收到的结算状态，导致客户端从
   结算弹窗退回旧牌桌，并且失去后续恢复保护。
3. 房主曾可能在结算阶段把暂时掉线的真人过早转为 AI，从而绕过真人确认屏障，造成两端页面分叉。
4. 新 peer 重进后，消息监听器、房间 roster 和座位恢复存在绑定顺序竞态；恢复握手发得过早时，
   房主看不到新 peer，无法把真人重新绑定回原座位。

当前处理包括：

- 真人结算确认使用严格屏障，结算阶段不能自动把真人转成 AI 并跳过确认。
- 新 peer 通过经过校验的 `playerId + seatToken` 恢复原座位。
- 新 Room 的消息监听器先同步绑定，再发送恢复握手。
- 客户端确认自己的新 peer 已进入权威 roster 后，只发送一次 roster-ready 握手。
- 房主在确认真人重进后，对当前结算执行一次延迟重放。
- 半开权威通道先做一次有界同步请求；仍失败则完整重进房间。
- 同一手已经接受的结算被视为不可降级事实，迟到的恢复消息不能把客户端退回结算前状态。

最终线上验收中，东1结束后能够正常进入东2，并继续完成两个完整东风场。

## 4. 同一原房间第二场曾经失败的原因

第一场结束后原房间仍然存在，本来就应能直接开始第二场。此前客户端停在大厅有两个根因：

1. 第二场房主引擎生成了新的 `authorityEpoch`，客户端旧门禁只允许通过 `rejoin_ok` 切换代次，
   导致第二场的 `round_start`、快照和回合请求被误判为旧权威消息。
2. 返回大厅时没有把上一场的 `round/honba/dealer` 生命周期归零，第二场的东1消息又被当成
   轮次倒退而丢弃。

现已允许“大厅状态下收到第二场东1的 `round_start`”建立新权威代次，并在返回大厅时重置
对局轮次生命周期。最终验收已证明同一房间第二场可以直接开局并打完。

## 5. 动画和结算必须重新观察的内容

下一轮不能只看牌局是否最终结束，两个真人端都要逐项观察：

1. 开局开始阶段正常出现，不应瞬间跳到完整手牌。
2. 第一骰显示两枚骰子；翻精方位按**两枚骰子点数之和**计算，不能只按其中一颗判断。
3. 翻精指示牌从正确玩家方位的墙段翻出。
4. 第二骰由正确方位玩家投掷。
5. 二骰后牌山断点切换正确；牌山不能在发牌结束时突然跳位或回跳。
6. 发牌动画完整，牌墙数量按阶段从 136 到 134，再随发牌批次递减。
7. 胡牌时房主端和客户端都播放胡牌特效，且同一事件不重复播放。
8. 胡牌后房主端和客户端都进入同一手的结算弹窗，分数与结果一致。
9. 仅一端确认时不能推进；两端都确认后应立即进入下一手，不应长时间等待。
10. 自动确认、仅房主先确认、仅客户端先确认三种路径都不能取消下一手的开局动画。
11. 第一场结束后回到原房间，直接准备并开始第二场；不要新建房间。

说明：莲花麻将第一骰规则使用两骰之和 `S = d1 + d2`。方位为
`(dealer + S - 1) % 4`；看到单颗骰子为 5，不能据此断定翻精应该在庄家面前。

## 11. 资源就绪与胡牌阶段专项修复（2026-08-20 续测）

线上续测房间 `EXWGVF` 在东1首次 Canvas 探针处停止，探针报告
`nonBlackRatio=0`，但双端全页失败截图都显示 3D 牌桌、牌山、暗手、牌河和副露正常可见。
本次属于 WebGL 后缓冲不可读造成的探针误报，但代码审查同时确认了两个真实生产缺口：

1. 牌面预加载原先使用 `Promise.allSettled`，单张图片最终失败仍会当作整体 ready。
2. VibeHub 客户端开局时间线虽然接收 `waitForTableReady`，但没有真正等待它。

已修复为严格资源门槛：

- 全部 34 张牌面各自最多重试 3 次，必须全部请求成功且完成图片解码。
- 资源成功后再创建 3D 图集，使用 `renderer.compileAsync(scene, camera)` 完成着色器编译。
- 主动提交首帧并跨过两个 `requestAnimationFrame` 合成帧后才发送 table ready。
- 任一资源最终失败时不发送 ready，持续显示明确的加载失败状态，并允许用户重试缺失资源。
- VibeHub 开场必须先取得同手权威快照、挂载牌桌，再等待 table ready；等待期间不得进入
  `start/dice/flip/deal`，也不得发送 `opening_done`。旧时间线取消后，即使迟到 ready 也不会推进。
- 线上黑屏检查改为读取浏览器最终合成的全页截图并按牌桌区域裁剪，不再读取 WebGL 后缓冲；
  加载遮罩仍可见、牌面请求少于 34 张或 WebGL context lost 同样判定为未就绪。

### 11.3 胡牌后三家手牌真实消失、协议修复与最新门禁

用户在房间 `XFKZ4B` 的场景 A 东2局结算画面提供了直接截图证据：本家最终手牌仍可见，
上、左、右三家的暗手区完全为空，也没有替换成亮明牌；牌山、牌河和副露仍在。这不是原子计数
误报。旧验收只检查 `concealedTileCount`，而远端脱敏快照会保留该张数、把真实牌面映射成空数组，
因此会出现“计数仍为 13、画面却没有牌”的漏检。

根因是结算协议同时发送公共 `round_settled` 和定向完整 `state_snapshot`，两者原先共用同一个
`sequence`。公共事实先到时，客户端会把随后包含真实牌面的同序快照当作重复包拒绝；公共事实本身
又不携带四家最终手牌，`revealHands` 开启后只有本家旧手牌可见，另外三家变为空手。

生产修复：

- 公共结算事实新增四家已经公开的最终手牌，严格禁止 `null` 暗牌占位；不包含剩余牌墙顺序。
- 公共结算事实使用较小序号，定向完整快照使用紧随其后的较大序号；无论 SDK 投递顺序如何，
  完整快照都能作为更新事实落地。
- 客户端收到公共结算时立即用四家公开手牌替换上一帧的脱敏玩家状态，再进入胡牌/结算时间线。
- 协议 decoder 要求公共结算包含四个唯一座位且所有手牌均为真实牌面，缺席、重复座位或 `null`
  牌面一律拒绝。
- 两份线上验收新增逐座位断言：亮牌阶段 `revealedFaceCounts` 必须有四项、逐项等于
  `concealedCounts`，且每家真实牌面张数均大于 0；不记录或保存任何具体牌值。

# 对局回放的 AI 分析记录补充方案

日期：2026-09-20  
状态：设计草案，尚未修改录制、导出或 AI 决策代码。  
首期范围：血流玩法，本地普通 AI 与接入 LLM 的 AI；其他玩法可复用公共结构，但须分别验证规则状态。

## 1. 目的与边界

让一手牌能回答五个问题：当时知道什么、允许选什么、实际选了什么、为什么执行成这样、分数如何变化。记录用于定位策略损失、复现问题及比较新旧策略，不能把「分歧」或「后来输了」直接标记成错误。

沿用现有展示回放，增加与之关联的决策记录和计分事件，不另建一套逐帧全量日志。录制只旁路采集当时已有的信息，不额外调用模型，不在出牌路径上运行反事实搜索，也不为分析强制计算所有候选的昂贵估值。

本地 AI 与 LLM 使用相同的局面、动作及执行记录。LLM 只额外增加请求、回答与回退链路。角色名、头像、`isLlm` 都不能证明某一手确由模型决定。

## 2. 现状与已知缺口

当前 `src/game/replay/types.ts` 的回放包含场次信息、开局锚点、摸／打／鸣牌／胡牌步骤、变化座位的手牌副露及分数、局末结果。血流录制器从旁观快照及累计动作流水生成展示事件；摸牌检测是尽力恢复，不能等同于权威决策前快照。

现有格式没有完整保存决策请求、合法动作集、策略过滤、当时推荐、模型回答、动作来源及执行回执。过牌和拒胡通常不能由展示流水可靠判定；多家竞争时，没执行的选择也不可见。

本次用户提供的八局 LLM 回放，在首次鸣牌／胡牌之前可核对的 72 个摸牌后弃牌窗口中，有 21 个实打牌种与当前本地 AI 不同。这只能作为缺口实例，不能作为整场分歧率，也不能证明都是模型主动改判。

## 3. 共同必需记录：本地 AI 与 LLM 都要有

### 3.1 场次级版本与配置

每场保存一次；局中发生变化则生成新配置记录，由后续决策引用。

| 内容 | 最小字段 | 用途 |
|---|---|---|
| 格式与引擎版本 | 格式版本、引擎构建标识、规则版本 | 判断能否准确复现 |
| 生效规则 | 计分、封顶、动作优先级等实际规则配置及指纹 | 规则名称相同不代表规则参数相同 |
| AI 配置 | 策略版本、实际参数与开关、配置指纹 | 区分 source-v2、legacy、机会约束及其他开关 |
| 座位控制方式 | human／local-ai／llm，变化时记录 | 接管或回退不能只看开局角色 |

配置指纹用于校验和去重，不能替代配置本身。导出包必须包含引用的配置。版本号也不保证旧代码永久可得；缺少旧实现时应标记「无法精确重执行」。

### 3.2 决策关联与准确前态

每个需要作出选择的座位窗口生成一个 `decisionId`，至少关联：

- `matchId`、`roundId`、`authorityEpoch`、`windowId`、`stateVersion`、绝对座位。
- 对应的决策前快照引用、源事件 ID、后续命令及展示步骤／结算事件引用。
- 窗口类型：摸牌回合、弃牌响应、抢杠等；当前源牌、来源座位、是否杠后补牌。

同一个公共窗口可以有多个座位决策；一个决策也可能对应多个展示或结算事件。不能假定一一对应，不能用时间接近代替 ID 关联。

决策前态取自权威引擎实际交给该座位的视角，至少包含：本家手牌及摸牌索引、副露、精牌；四家公开弃牌、副露、分数；庄家及局数；墙余；锁手状态、公开胡牌与杠记录；当前合法动作和本家可胡计分。对手暗手、未摸牌墙和私有拆解不进入该视角。

能从权威事件准确还原的字段使用引用或增量；不能从展示回放准确还原的字段必须补存。每份状态带校验指纹，不能把动作后的手牌当作决策前手牌。

### 3.3 合法动作、策略候选与选择

明确区分三个层次：

| 层次 | 保存内容 | 说明 |
|---|---|---|
| 引擎合法动作 | 窗口内合法动作集 | 回答规则允许什么 |
| 策略候选 | 过滤后的候选、被限制动作及原因码 | 回答模型／本地策略实际能选什么 |
| 策略输出 | 推荐动作、实际选择、所用配置引用 | 回答最终选了什么 |

候选使用窗口内稳定 ID，同时保存规范化动作。弃牌保留当时手牌索引与牌种；吃牌保留组合；补杠关联副露。分析普通弃牌分歧时按牌种比较，避免把同牌不同索引误算成策略差异；涉及摸切或锁手时仍保留索引语义。

估值只保存当时已计算且用于选择的量：即时收入、预测后续收入、风险成本、综合分、改张阈值、硬性限制原因。注明单位、预测范围及是否计入支出；启发式分数不能冒充点数净收益。没有计算的字段标记缺失，不填零，不为凑齐表格新增在线计算。

本地 AI 的推荐通常就是其选择，不必重复存两份。LLM 的本地推荐必须记录真正送给该次请求的推荐，不能事后用新版 AI 补算并称为「当时推荐」。

### 3.4 动作来源与执行回执

分开保存「谁选择」和「引擎最终执行什么」：

- 选择来源：本地策略、模型回答、模型失败后的本地回退、人类、规则自动动作、倒计时兜底。
- 实际选择、提交命令 ID、提交结果、执行事件引用。
- 状态与原因：已执行、已接受但被更高优先级动作压过、窗口已过期、局面已变化、动作非法、请求取消等。原因以实际运行分支为准。
- 选择了过牌也要保留；只有当时存在合法胡牌候选且主动选择其他动作，才可以标记为拒胡。

不将「没有观察到胡／碰」推断为主动过牌，不将已接受的低优先级选择记成模型错误。锁手后的强制动作可用精简记录，只保存关联、来源和执行结果，不重复生成无意义的候选估值。

### 3.5 决策时间

保存窗口开放时间、决策开始、完成、提交及截止时间。耗时使用本进程单调时钟，跨端关联使用事件 ID；不直接相减不同设备时钟。

本地 AI 保存计算耗时与超时情况。LLM 按请求尝试补充发送、收到完整最终回答、取消或失败时间。首字节时间只有现成可取且确有诊断用途时才保留。无需逐 token 时间流水。

## 4. LLM 专有补充

| 内容 | 最小记录 | 分析价值 |
|---|---|---|
| 实际模型配置 | 供应商标识、请求模型 ID、可得的返回模型版本、影响决策的采样／思考开关 | 角色名不能代表实际模型；未返回版本则明确未知 |
| 请求关联 | requestId、decisionId、attemptId、重试序号 | 一次决策可能多次请求，但只执行一次动作 |
| 请求内容引用 | 提示词模板版本／内容指纹、实际变量输入、候选及推荐引用 | 重建模型真正看到的信息 |
| 最终回答 | 原始最终回答正文、解析后的候选 ID、简短说明 | 区分判断差异、解析问题与非法选择 |
| 请求与解析结果 | 成功、网络错误、超时、取消、解析失败、候选不存在等 | 判断损失发生在哪一层 |
| 回退链路 | 触发原因、使用的回退配置、回退动作、最终执行回执 | 避免把本地兜底动作归因于模型 |

模板按版本去重存一次，决策保存实际变量输入；若动态拼接内容无法由模板和变量重建，必须保存缺失部分。单存提示词哈希不足以复现。候选说明若影响模型选择，也是输入的一部分。

最终回答指模型输出给应用的决策内容，不是内部思考过程。模型说出的理由只用于排查，不当作决策正确或收益提高的证据。系统另行生成的角色台词、语音不得冒充决策理由。

Token 用量和服务端请求标识只在接口已有返回时附带；无须为它们新增请求。禁止保存 API Key、Authorization、Cookie、完整请求头或带凭据的服务地址。

## 5. 结构化计分流水

优先复用血流权威账本，每次结算引用保存一次，不在每个决策重复复制。

至少包含结算 ID、局 ID、源事件 ID、胡／杠类型、赢家及付款座位、各家分数变化、结算后分数、计分构成和封顶处理。同一张牌的一炮多响保留同源关系。

由此派生自摸收入、点炮收入、放炮支出、其他付款和杠净收益；不额外维护容易与账本漂移的重复累计字段。每次结算与整场校验分数守恒，并与展示回放结算一致。

## 6. 精确复现所需的赛后私有数据

若要在原牌墙上改变动作并重跑后续，每局保存一次完整初始物理牌墙、庄家、骰子、翻精／开墙参数及开局分数。保存牌墙优先于只保存随机种子：随机算法或发牌实现变化会使同一个种子产生不同牌局。

还需要完整权威动作／过牌命令及执行顺序；仅有牌墙和展示步骤不足以精确复现。存在其他随机决策时，保留对应算法版本与种子。不得声称能依靠这些信息让外部 LLM 再次生成完全相同回答；原局复现使用已记录的实际动作。

这部分单独标记为赛后私有数据。本地录制从权威引擎获取；联机场景不能为了分析向普通客户端提前泄露牌墙或对手暗手，只能由有权限的权威端在局后提供。无法提供时明确标记复现能力不足，不猜测补齐。

原牌墙反事实用于复现具体事件；判断策略优劣还应在符合当时可见信息的隐藏牌分布下重采样。原局中「实际摸到了好牌」不能作为当时可知的依据。

## 7. 建议的数据组织

在现有导出包增加独立、可选的分析区，而非给每个展示步骤堆满字段：

| 区域 | 保存频率 | 主要内容 |
|---|---|---|
| configurations | 每版本一次 | 规则、策略、模型与提示词配置 |
| decisionStates | 每状态一次或引用增量 | 准确的单座决策前态 |
| decisions | 每座位决策窗口 | 候选、选择、来源、耗时、执行关联 |
| llmAttempts | 每次实际请求 | 输入引用、最终回答、失败与回退信息 |
| settlements | 每权威结算一次 | 计分账本及事件关联 |
| reproduction | 每局一次 | 赛后私有牌墙、开局参数、权威命令 |
| recordingStatus | 每场／局及异常点 | 支持能力、缺失段、截断或落盘失败 |

分析模块必须区分「原始观察」「依据明确规则派生」「未知」。导出时引用闭合；不能只有 ID 而丢了对应状态或配置。

## 8. 优先级与明确不做的事

### P0：能归因的最小闭环

先完成决策 ID 与准确前态、版本配置、合法／策略候选、选择与执行回执、过牌／拒胡、动作来源和关键耗时。LLM 同时补请求关联、实际推荐、最终回答及失败／回退记录。§9 的可选录制、增量去重、压缩分块、字节预算与降级必须同期完成，不能先上线全量快照录制再补容量治理。

P0 完成后，才能可靠统计「真正由模型选择的动作与当时推荐有多少分歧」「多少动作实际来自回退」。不要求先做分析仪表盘。

### P1：能复现、能计算损失

接入权威计分流水、赛后私有开局数据和完整命令序列，提供离线校验与复现工具。接入当时已有的关键候选估值；缺失估值可以离线用指定版本重新计算，但必须注明是重算值。

### 暂不做

- 不录内部思考、音频、完整网络日志、逐 token 流水和重复提示词全文。
- 不保存每一渲染帧的全量状态，不为无选择的自动动作计算完整候选特征。
- 不在对局过程中额外跑新旧 AI 对抗、模型交叉评审或反事实搜索。
- 不自动贴「错打」「最优」「模型变强」标签，不把一场输赢作为训练标签。
- 不默认上传回放；公开分享版本与含私有复现数据的分析版本明确区分。

## 9. 兼容、体积和失败处理

### 9.1 容量基线与估算边界

以下基线由用户提供，采自与线上一致的单局血流代码路径，本次文档修订未重新测量；新增分析区的数字仍是设计估算，不是已实现的压测结果。KB／MB 沿用提供者的近似口径，实施时统一按 UTF-8／二进制字节记账。

| 项目 | 单局量级 | 性质 |
|---|---:|---|
| 决策窗口 | 88 个 | 用户实测 |
| 单座决策视角 | 平均 8.2KB，最大 26KB | 用户实测，不能逐窗口整份持久化 |
| 旁观视角 | 平均 11.3KB，最大 31.7KB | 用户实测，不是分析输入 |
| 现有展示回放 | 54.7KB，169 步 | 用户实测 |
| 全量决策快照 | 约 0.72MB | 88 × 8.2KB 的推算，尚未计候选与回答 |
| 重复全文提示词 | 约增加 0.3–0.5MB | 约 44 个 LLM 窗口的估算 |
| 增量、去重后的方案 | 约 0.36MB | 用户估算，待实际字段验证 |
| 初始牌墙与命令序列 | 约 20KB | 用户估算，低成本、高复现价值 |

朴素方案可能达到半庄约 9–10MB、50 场约 450–500MB；增量方案约半庄 3MB、50 场 150MB。若分析 JSON 压缩至原来的 1/5–1/8，用户估算总量约 20–40MB。实际必须分开计展示回放、分析块、索引／元数据及写入临时空间，不能将所有占用直接乘同一压缩率。

按 54.7KB/局线性推算，现有 50 场纯东风场约 11MB、纯半庄约 22MB，实际随局数和记录内容变化。容量测量应统一序列化、压缩与数据库口径，不能把文件缩进大小、JSON 字符数和数据库占用混为一谈。

实施时新增一个离线容量基线工具（尚未实现），固定使用同一次真实半庄、相同导出选项和输入校验值，同表报告：无缩进 JSON 的字符串长度（注明 JavaScript UTF-16 码元数）、UTF-8 字节、各分析块 gzip 后字节及汇总、应用落库字节账本、导出包实际字节。另在隔离浏览器测试环境记录写入前后同源 usage／quota 估算和可取得的开发工具 IDB 占用读数，注明浏览器版本及测量方法。没有数据库级实测接口时填「不可得」，不能把 `estimate()` 的同源差值标为单场 IDB 精确占用。展示、分析、共享配置分别列出，首次落库与复用配置后的增量分开测量。

上述估算只说明增量与压缩有明显价值，不保证任何浏览器一定存得下，也不把 200MB 当作跨设备安全配额。用户给出的浏览器配额／回收判断未在本次验证；实现验收以实际环境和配额错误处理为准。

### 9.2 两层存储，分析录制可选

展示回放继续正常保存；分析区独立存储、独立计费和清理。初期分析录制默认关闭，由用户开启；关闭时不构造分析快照、不生成额外估值或请求。开启后覆盖所有符合条件的决策，不只记录事后看起来有问题的窗口。

每场显示分析状态：未开启、完整、部分缺失、已删除。支持单独导出分析包、单独删除分析区而保留可观看回放；删除后明确失去哪些分析能力。分析包必须包含其依赖的局面／配置，不能导出一堆只能在原数据库解析的引用。导出成功不自动等于可以删除，清理由明确操作或既定保留政策触发。

分析区的生命周期与所属场次绑定，不能比它引用的展示回放活得更久。展示回放被其保留策略裁掉（总预算或场数上限，见 §9.4）时，该场的分析块同步删除，界面说明「已随场次移除」；不得留下「展示回放已删、分析区引用悬空」的状态——§9.3 把公开字段的唯一来源定为展示回放，悬空即等于该场分析永久不可读。受保护标记只表示不被选作淘汰候选，不等于可以脱离其展示回放长期存在；后台写入、导出或恢复流程也不能让分析块指向已被清理的场次。

需要长期留存某场分析时，出口是导出**自包含**分析包（含其依赖的局面、配置与赛后私有复现数据，见 §6、§7），而不是把引用留在库里等待其展示回放消失。删除场次与分析块时，按 §9.4 的依赖清单核对容量账本与引用计数；顺序上先解除引用再回收共享配置，避免出现「配置已回收、仍有块指向它」的中间态。

### 9.3 禁止重复快照，压缩二进制分块落库

决策前态采用权威检查点加增量／事件引用，恢复不出的字段才补存。手牌也不要求每窗口重复保存：若已能精确恢复，只保留状态引用与校验。候选、估值及回答按实际需要保存，不能重新嵌入完整座位视角、重复历史账本或全文提示词。

**展示回放已准确覆盖的公开字段，以展示回放为唯一存储来源，分析区不得重存一份。** 引用必须定位到决策前的权威状态版本，而非只选时间最近的展示帧；展示流未覆盖的公开字段才增量补齐。这里的「公开」不包含旁观回放里的对手暗手，恢复分析输入仍须按座位遮蔽。

- 摸后打窗口：若摸牌步骤完整且校验为该决策的前态，复用其手牌及折叠后的公共状态；不能假定尽力恢复的每个摸牌事件都准确。
- 响应窗口：吃／碰／杠／胡的过牌或拒胡可能没有新的展示步骤。增加窗口级检查点关联，核对响应座位的手牌与摸牌索引；锚点和历史增量能精确恢复就引用，不能恢复才补存该座位差量或必要手牌。合法动作、本家胡牌计分和缺失的规则状态亦按需补存，不能仅引用弃牌者的动作后状态。
- **已知格式缺口，属于实现前置项**：现有 `ReplayStep` 只记录动作座位的手牌变化，以及被鸣牌带走弃牌的 `sourceDiscards` 与来源座位 `from`，**不含响应座位在该窗口的手牌与摸牌索引**；而血流录制的摸牌检测本身是「手牌数 +1 即视为摸牌」的尽力恢复（见 §2），不能当作权威决策前态。因此响应窗口的前态必须有新增来源，二选一并明确标注：① 录制侧由权威视角为每个窗口生成检查点（推荐，权威端本就有该视角）；② 分析区按座位补存差量。不得默认「展示回放已经覆盖」，也不得用时间最近的展示帧顶替。

代码核对确认 `src/game/replay/transfer.ts` 已有 gzip／解压与校验逻辑，但当前用于传输，最终还会转为 base64。存储实现应抽取复用压缩能力，以压缩二进制块保存，不照搬网络分片／base64 包装，也不把「已有传输压缩」当成「IndexedDB 已压缩」。

落库载荷统一使用 `ArrayBuffer`／`Uint8Array`，不保存为 `Blob`，不 base64；这是本项目的存储格式约束，不宣称 Blob 在所有浏览器都不可用。base64 每 3 字节变成 4 字符，另有尾部填充，没有必要为本地落库增加这层体积。压缩流程内部临时使用 Blob 与最终存储格式是两回事。

按局内有界批次压缩，块完成后不可变追加；不每出一手重压整局，更不把整场留在内存等结束。压缩在写事务之前完成，事务只写已经准备好的块与索引。记录编码、压缩前后字节数、校验值和序号；读取按需解压，不在打开回放列表时解压全部分析记录。解压也设置输出大小限制。

首版采用「按局分组、局内多个物理块」：按未压缩 UTF-8 字节累计，目标达到 **32–64KiB（32768–65536 字节）** 后压缩写入，不逐条 gzip。局末及达到有界刷盘时间时允许写入不足目标的小尾块，刷盘时间随首期延迟／丢失范围测试冻结；不依赖页面关闭回调保证落盘。单条超大回答按可重组片段分块，保持原文完整并受总预算约束。32–64KiB 是首版批量目标，需测量压缩比和峰值内存，不是收益保证；不能一概断言 1–3KB JSON 单条压缩没有收益。

压缩不可用或失败时，原始块只有在字节预算和队列限制内才允许保存，否则暂停分析录制并记录缺失。不得无条件降级成大体积原文。压缩不能替代去重与容量上限。

### 9.4 字节预算优先，场数为辅助限制

保留策略采用「回放总字节预算 + 分析区子预算」，同时保留可配置场数作为辅助上限。场数从 50 调到 200 不自动扩大字节预算。200MB 可作为可配置软上限候选，正式默认值待设备实测确定，不能直接作为所有环境的默认承诺。

逐块累计实际保存的二进制字节及元数据估算；这是应用账本，不冒充浏览器物理占用。浏览器可用容量信号只能辅助下调预算，不能保证下一次写入成功。留出当前局、其他应用数据及临时写入余量；并发录制／导入需要协调预算和淘汰，避免各自判断未超限后同时写满。

同一浏览器配置文件、同一存储分区内的同源多标签页共享存储预算；不能只测单页或两个独立浏览器。预算预留、提交记账、释放和清理应跨实例协调，不能只靠内存锁或各页自己的计数。测试两页同时录制／导入、关闭一页后恢复遗留预留、重复删除与额度竞争；来源不同或分区隔离的上下文不能误当成同一账本。

实现清单纳入 `navigator.storage` 的能力探测及拒绝／失败分支：首次启用分析录制时检查 `persisted()`，未持久化则在这次明确用户操作中尝试 `persist()`，保存获准／拒绝／不支持状态，不在每次开局反复申请。持久化不能替代预算，也不是空间预留或永不丢失保证。启动、批量导入／清理后及有节制的定期检查调用 `estimate()`；它用于判断同源存储压力，不能按其读数覆盖本应用的逐块账本，账本偏差需扫描已存块修复。当前 replay 目录未发现这些调用，属于待实现项。接口语义依据 [WHATWG Storage Standard](https://storage.spec.whatwg.org/#api)。

达到预算时按以下顺序处理：

1. 优先按最近查看／分析使用时间，淘汰未保护的历史分析区，先保留展示回放。后台写入不刷新历史记录的使用时间。
2. 若仍无法容纳新分析块，暂停本场分析录制并标记缺失，继续游戏和尽力保存展示回放。受保护记录及正在写入的局不被自动删除。
3. 展示回放自身达到总预算时，按其保留政策清理未保护的旧场。不能为了继续分析录制，优先删掉用户可观看的历史回放。**场次被裁掉时同步删除该场的分析块**：分析区不得比它引用的展示回放活得更久（§9.2），裁剪后若出现「分析块仍在、展示回放已删」即视为账本修复对象，先按引用清单清理再继续写入。
4. 无可清理空间时明确提示容量不足；导出／删除入口可用，不无限重试、不阻塞出牌。

删除分析数据与对应索引、引用计数、容量账本保持一致。共享配置／模板放在独立配置区，以场次或分析包的依赖清单维护引用计数，只有零引用时才回收；不要把其他场次依赖的配置放在某个可单独删除的场内。活动局也持有有效引用。必测「A、B 两场共享模板→删 A→B 可完整分析→删 B→零引用配置回收」，再覆盖重复删除和中途失败，验证计数不会少减、多减或变成负数；恢复时能按依赖清单核对账本。

### 9.5 兼容、写入失败与验收

旧回放继续可导入、观看，标记「缺少决策分析记录」，不得因新增字段而清空已有历史。当前格式版本检查及存储淘汰逻辑需要单独审查，不能只递增常量就丢弃旧记录。

录制采用有序且有字节上限的异步队列，不因写失败无限堆积内存。单局 88 次决策并不是同时写入的事务大小，必须分别测量单块大小、写入频率和队列峰值。配额错误最多在完成一次可回收清理后作有限重试，失败则暂停分析；录制逻辑不得抛错影响权威动作执行。

既有实现参照：`src/game/replay/storage.ts` 的 `guard()` 捕获错误、调用 `onError` 并停用该存储实例的 driver；`storage.test.ts` 覆盖写入失败降级，`recorder.test.ts` 用 `new Error('quota')` 同时覆盖同步抛错和异步拒绝不打断对局。复用其错误隔离原则，但分析失败不能连带停用仍可工作的展示存储实例；失败通知自身也必须安全。现有 guard 不会自动回收重试，上述有限清理重试需在分析层明确实现，不视为已有能力。

若容量、队列或写入失败导致不完整，记录缺失起点／范围与原因；不能静默截断回答后仍标记可复现。数据库连状态元数据也写不进时，至少在内存与界面标记失败，下一次恢复后补记；用已提交块的连续序号识别中断，不保证断电前未落盘的数据仍可恢复。

首期测量真实半庄和长回答样本的原始／压缩体积、压缩比、压缩与写入耗时、队列峰值、列表加载和导出峰值内存。验证低容量、压缩不可用、写失败、关闭页面、分析区清理和 200 场索引场景。20–40MB 作为待验证估算，不作为通过标准；上线前固定实际字节预算、块／队列上限，并验证超限按上述政策降级。

正确性门槛包括：录制开／关不改变策略动作和对局结果，不触发额外模型请求，不影响窗口截止处理。分析区删掉后仍能看牌谱；缺失分析数据时不能继续声称完整复现。

## 10. 实施后的验收清单

1. 本地 AI、LLM 成功、LLM 超时／解析失败回退、强制动作均能正确识别来源。
2. 迟到回答、重试和取消不会串到下一窗口；请求成功不等于动作执行成功。
3. 过牌、拒胡、竞争失败、一炮多响均能与权威事件对应，不靠显示快照猜测。
4. 导出的决策输入只含当时合法可见信息；私有牌墙和对手暗手不进入 AI 输入。
5. 计分流水与引擎结果一致且守恒；本地 AI 在相同版本与配置下重算动作一致。
6. 完整记录可以重放到同一结束状态；不完整记录明确拒绝宣称精确复现。
7. 旧格式可观看，新格式导入导出无丢失引用；录制关闭时没有额外计算或 API 成本。
8. 分析区增量去重、压缩落库和字节预算实测有效；压缩失败、配额不足及队列满可控降级，清理不破坏展示回放或受保护记录。
9. 摸后打与响应窗口分别验证前态恢复；已有公开数据不重复存储，过牌／拒胡窗口缺失的座位状态被准确补齐。
10. 同源两标签页并发记账与清理正确；删场后其他场次的共享配置依赖完整，最后一个引用移除后才回收。
11. 固定半庄容量工具分别报告字符数、UTF-8／压缩／导出字节、应用账本及浏览器估算；持久化被拒或接口不可用仍可按预算安全降级。

完成上述基础后，再从独立回放中筛选分歧窗口、做配对反事实，并在未参与调参的回放及新种子上验收策略。记录基础设施不等于策略提升，二者分别验收。

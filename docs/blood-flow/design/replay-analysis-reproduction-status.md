## 2. 四个根因（都是记录/匹配侧的缺陷，不是重放策略问题）

按发现顺序，每条都有实测证据：

1. **牌名两侧写法不同，匹配时只归一了一侧。**
   录制侧 `analysisCommandEntry` 存的是**牌码**（`tile: 'south'`），校验器却拿 `tileName(action.tile)`
   （显示名 `南风`）去比 ⇒ 任何带单张牌的吃/碰/杠命令都会被判"对不上"。
   证据：失败信息里 `同类候选={"kind":"concealed-kong","tile":"south"}` 与记录条目**逐字相同**却判否。
   修法：`actionMatches` 用 `tileName` 把两侧都归一（它对牌码幂等，显示名原样返回）。
2. **本端决策分支漏传 `windowId`。**
   `actBot` 里 `decisions.decide()` 返回动作的分支（单候选窗口、锁手窗口——`bloodFlowAiActions().length === 1`
   时本地直接决策）记录命令时没带窗口归属。后果有两层：校验器看不见"该窗口已有命令"
   （前置过滤失效，记录里该窗口只剩 `expire`），且**无编号条目被排序甩到整个序列末尾**。
   证据：失败现场"重放见过 36 个窗口 / 记录条目涉及 37 个窗口"、该窗口在记录中的条目只有 3 条 expire。
   修法：把 `windowId` 传下去（顺带把 `windowKind` 也记上）。
3. **漏记 `openingScores`（当局开局分数）。**
   §6 明列必需字段，录制侧一直没写 ⇒ 重放每局都从初始分 2000 起步。表现是"能跑完全部条目、
   但结束分数对不上"。证据：四局里后三局的差值**恰好等于**"当局开局分 − 2000"，
   而逐家净变化与权威端完全一致（这正说明牌流其实已经逐条吻合）。
   修法：`beginEngine()` 记 `openingScores`（与传给引擎的 `opening.players[].score` 同一时刻读）。
   同时校验器改为**缺开局分数就明确拒绝比对分数**，不再拿"从初始分起步的结果"冒充一致。
4. **`expire` 条目不带窗口类型（§11 的诊断能力缺口）。**
   没有 kind 就无法区分"记录侧多压/少压 expire"与"权威端推进方式与记录不一致"。
   修法：`expire` 条目带 `windowKind`（排定计时器时看到的窗口类型）与 `waitingSeats`；
   校验器把「记录侧同编号窗口的 kind」与「重放当前窗口的 kind」逐点对照，并把不一致次数
   （`kindMismatches`）作为结果字段返回。

## 2.5 接线分析区时发现的第五个缺陷：分析区与展示回放不是同一把钥匙

补 §9.2 的列表能力（状态显示／导出分析包／只删分析）时，列表对本场显示的是「分析：未开启」，
而分析库里明明有这场 1600 条记录 —— 由此查出真缺陷：

- 分析录制在 `phase=opening` 就 `analysis.start()`，而展示回放的场次记录要到 `roundStart` 才建立；
- 两边各自 `createId()` 生成 UUID ⇒ **分析区的 matchId 与牌谱的 matchId 从来不是同一个**；
- 后果一：`reconcileAnalysisWithReplay(analysisStorage, 牌谱清单)` 把刚打完那场的分析数据
  当成"展示回放已不存在的悬空分析区"**整场删掉**（§9.2 的回收逻辑本身没错，是两把钥匙对不上）；
- 后果二：列表无从显示该场分析状态，也无法按场次导出/删除分析。

修法：`ReplayRecorder.ensureMatchId()` 预留场次 id，`roundStart` 建场时复用它（预留与建场谁先谁后都对），
`App.vue` 与 e2e fixture 都用它开分析场次。回归：录制器单测 4 项（预留复用／重复调用同一 id／
场中取当前 id／下一场换新 id）+ e2e 状态断言（若两把钥匙再错开，状态会退回「未开启」而立刻失败）。

## 2.6 第六、七个缺陷：中途退出的两条路径都没收尾

查"未打完整场"这条路径时发现两个真问题（都在中途退出/换场处）：

1. **已录数据被静默丢掉**：`analysis.finish()` 只在 `matchFinished` 时调用；中途退出既不刷队列也不落库，
   下一个场次 `start()` 时旧录制器连同缓冲一起被替换 ⇒ 那一段记录无声消失（§9.5 明确"不能静默截断"）。
   修法：`returnToLobby()` 里判断整场未打完（`!matchFinished`）时，先 `noteGap({ scope:'match', reason:'match-aborted' })`
   再 `finish()` —— 已录数据落库、状态如实标 `partial`、缺失原因留痕。
2. **下一场挂到上一场名下**：会话端口 `port.finish()` 只结束录制器、**不清会话 target**，
   于是 `session.active()` 恒为真；App 的守卫 `if (value !== 'opening' || analysis.active()) return`
   会跳过下一场的 `start()`，新对局的决策/前态/复现全部写进上一场的 matchId（错场归属）。
   修法：代理的 `finish()` 与 `session.finish()` 共用同一实现（刷队列 → 写缺失 → 清 target）。

回归：会话单测（代理 finish 后 `active()` 为假、下一场换新 id、上一场不再被追加）+
e2e `analysis-abort.spec.ts`（真实引擎：打 12 个窗口 → 返回大厅 → 第一场 29 条 `partial` + `match-aborted`；
再开一场 → 新 id、23 条 `complete`）。

## 3. 关于 `expire`：记录里为什么曾经这么多（现在已经归零）

曾经 `analysis-size.json` 里 expire : command ≈ 1428 : 506，看着很吓人，它是**两条事实**的叠加：

- 主线程的截止计时器会把"窗口还是我看的那个"当作到期处理 —— 在 e2e fixture 里所有定时器被压成 0ms，
  于是这条在窗口刚打开时立刻触发；
- 权威端（worker）真正执行 `engine.expire(now, windowId)` 时会检查 `now >= deadlineAt`，
  提前发出的请求是**无操作**（fixture 里 15s 的截止时间从未真正到期）。

**2026-09-21 起录制侧改成「只记权威真正做的事」**：worker 回传 `expireAdvanced`
（`expire` 前后引擎版本号／窗口 id 是否变化），无操作的 expire 不再入列；`actBot` 提前返回时
也不再补记（那条同样是噪声：窗口其实由命令闭合）。实测四局的 expire 计数归零、
`metrics.expireSkippedByFilter` 归零，复现记录只剩真实命令。

推论（仍然成立）：**真实对时器下，某个窗口没人决定时那条 expire 就是必需的**，
所以保留"入列 + 重放侧按记录顺序应用"的机制，只是不再记录空转的 expire；
校验器的两条消解规则（同窗口有真命令则前置过滤丢弃；编号与重放当前位置不符则丢弃）作为旧记录的后备。

## 4. 复现校验器的工作方式（`src/game/replay/analysis/replayReproduction.ts`）

1. `openingFromReproduction` 把记录还原成引擎开局（**缺任何必需字段都明确失败**，绝不用默认值顶替）；
   并回报开局分数来自哪里（`scoresSource: record/base/missing`）；
2. 记录按**窗口编号稳定排序**后消费：命令 → 还原成当时的合法动作并提交；`expire` → 推时钟过截止时间再 `expire`；
   `auto` → 明确报"该窗口不是本端决定、记录不含其选择"；转场（`engine.transition`）→ 自行 `advance`（可推导，不需记录）；
   带 `accepted === false` 的条目一律不消费（权威从未执行它，§3.4）；
3. 比对结束分数（有期望分时；缺开局分数则拒绝比对），并返回 `kindMismatches`、推进来源计数
   （`metrics.expireApplied / expireSkippedByNumber / expireSkippedByFilter / rejectedCommands`）。

## 5. 已确证的结论（都经过实验或实测）

1. **worker 回传生效**：`{kind:'bot'}` 把权威机器人实际提交的动作回传（`botAction`），真实录像里 `auto` 完全消失；
2. **`expire` 条目必需**：第 61 轮试过"下一条真命令能落当前窗口就跳过这条 expire" ⇒ 第 1 局从成功退回失败；
3. **两侧窗口 id 不可比，但末尾编号可比**：记录 `round-2/window/36` vs 重放 `verify/2/window/36`
   —— 两侧都是各自引擎的自增版本号，**编号相同通常对应同一位置**（这正是 kind 对照能成立的前提）；
4. **编号相对判定有效**：据此丢弃"不属于当前窗口"的 expire 后，偏移从 +3/+5 降到 +1；
5. **前置过滤（同窗口有命令则丢弃 expire）保留更好**：第 56 轮（单次运行）与第 72 轮（两次运行）两次停用实验都未改善；
6. **吃/杠必须按牌集合匹配**：这类动作不带单张 `tile`（用 `tiles/meld` 表达），只比 `kind` 会吃错组合；
7. **到点静默的座位原先不留任何条目**：`actBot` 在"到点或已不再等待"时提前返回 ⇒ 该座位在记录里凭空消失；现已补记 `expire`；
8. **可推导信息不要记录**：转场、`headDrawn` 等由引擎状态推出即可，记录它们只会引入不一致。

## 6. 已排除的路径（不要再走）

- **"跳过 expire"的两种变体**：第 61 轮（下一条真命令能落当前窗口就跳过）、第 98 轮（窗口编号前瞻）
  —— 两次都让 `replayProgress` 明显变差（第 98 轮降到 12%~20%）。expire 必须按记录应用，
  问题出在**记录本身不完整**，不在"要不要应用"。
- **条目缺失 / 条目顺序 / 组合动作的 index 判等**：都查过，不是根因（index 判等对组合动作本来就不该比）。
- **"两侧窗口序列不对应 ⇒ 重放推进方式有问题"**：方向错。真正的原因是记录里那些命令**没有窗口归属**，
  排到末尾后重放自然错开一位。

   该编号的全部条目（含 `[kind]` 与 `等待=[…]`）、expire 判定计数、`kindMismatches` 与最近一次不一致；
2. **`tests/e2e/analysis-probe.spec.ts`（快速探针，推荐首选）**：只跑一场血流，把
   **完整分析记录 + 权威窗口轨迹 + 逐局回放结果**落到 `tmp/analysis-probe.json`，一次约 25~35 秒
   （整条 `replay.spec.ts` 要 1.5 分钟以上且夹着大量 UI 断言）。断言只做记录格式护栏，
   复现结论看 `replayProgress` / `replayReasons` / `kindMismatches`。

## 8. "先确认信号可信"——本项目踩过的元错误

排查 §10.6 时，真正拖慢进度的不是功能缺陷，而是**观测信号本身不可信**。以下都是实际发生过的：

1. **陈旧模块**：e2e 页面里跑的仍是旧版校验器（Vite 转换缓存），新加的诊断字段完全不出现。
   **对策**：改完校验器先做"新鲜度自检"（断言某个新诊断字段出现在输出里），必要时用
   `pnpm dev -- --port 4173 --force` 重启。
2. **诊断读错字段**：读座位视图**顶层**的 `hand`（实际不存在）⇒ 恒为 0，产生过假信号；
   正确位置是 `players[seat].hand`。**对策**：诊断字段先确认来源再据其下结论。
3. **诊断与生产口径不一致**：诊断按"窗口编号"匹配、生产按"完整 windowId"匹配 ⇒ 结论分叉。
   **对策**：诊断与判定用同一口径；输出完整标识而不是截断后的部分。
4. **误判自己的判据**：曾以为 e2e 的 `replayOk` 偏弱而打算"补期望分"；重看断言后发现组合断言已有效。
   **对策**：改判据之前先把现有一组断言读全。
5. **把"夹具特性"当成产品行为**：fixture 把所有定时器压成 0ms，于是"截止计时器立刻触发"是夹具产物，
   不是线上行为。**对策**：结论里注明它依赖哪条夹具假设（如"expire 无操作"只在 15s 截止从未到期时成立）。
6. **只归一了一侧**（本次根因之一）：记录存牌码、候选经 `tileName` 变显示名，比较时只归一候选。
   **对策**：凡"两侧对等比较"的字段，先确认两侧的规范化口径一致，并写一条两侧写法混用的回归用例。

## 9.5 与本次工作相关的两个额外修复

- **表格卸载竞态**（`MahjongTable3D.vue`）：three 的 `compileAsync` 用 `setTimeout` 轮询
  `checkMaterialsReady()`，卸载时若已 `dispose()`，轮询里 `materialProperties.currentProgram` 变成
  undefined ⇒ 抛 `Cannot read properties of undefined (reading 'isReady')`（快速进出回放视图必现，
  e2e 的 `pageerror` 断言抓到）。修法：记下未完成的 `compilingShaders`，卸载时等它结束再释放场景与渲染器；
  等不到就只丢引用（宁可少释放一次，也不要抛未捕获异常打断整页）。
- **dev server 被原子写临时文件搞崩**：Agent/编辑器写文件是"临时目录 + 改名"，Windows 上 Vite watcher
  去 watch `*.tmpdir/*.tmp` 会拿到 EBUSY，而 Vite 对 watcher 的 error 是致命的 ⇒ dev server 退出，
  正在跑的 e2e 立刻 `net::ERR_CONNECTION_REFUSED`（本会话发生了 3 次）。修法：`vite.config.ts` 的
  `server.watch.ignored` 忽略这类临时产物。

## 12. 容量基线实测（§9.1、§10.11）

固定输入：半庄 8 局、固定种子牌墙（`?mode=hanchan&seed=83`）、分析录制开启、autoplay 本地对局；
报告落在 `tmp/analysis-capacity.json`，用 `pnpm test:e2e -- analysis-probe` 复算：

```
分析记录 2745 条：config 1、decisionState 982、decision 1253、responderCheckpoint 321、settlement 180、reproduction 8
无缩进 JSON：1749720 个 UTF-16 码元 / 1752681 字节（UTF-8）
分块：40 块（gzip）；原始 1711.6KB → 落库 138.4KB（压缩比 8.1%）
应用账本：138.4KB / 1 场 ⇒ 单场 138.4KB
元数据 JSON：0.3KB；IDB 索引与页开销：不可得（无数据库级接口）
展示回放：480.8KB
自包含导出包：2195.3KB（含 2 空格缩进；相对落库 15.86×，两者口径不可混比）
浏览器估算：usage 0.17MB / quota 6144.17MB（同源估算，不是本应用账本）
持久化状态：denied（无头 Chromium 拒绝了 persist 申请 —— 拒绝路径已被真实覆盖）
线性推算（不是保证）：50 场 6.76MB；200 场 27.03MB
```

结论与设计估算的对照：

- **分析区比设计估算小得多**：§9.1 预估"增量去重后约 0.36MB/半庄"，实测**138KB/半庄**（压缩比 8.1%）；
  50 场 6.8MB、200 场 27MB，都在 §9.1 的"20–40MB"区间内。
- **展示回放才是大头**（480.8KB/半庄，与 §9.1 的 54.7KB/局 一致）：200 场约 96MB。
  因此 §9.4 的字节预算必须**分开计**展示回放与分析区 —— 这也正是"分析区不得比展示回放活得更久"的另一面。
- 导出包远大于落库字节（15.86×）：因为导出文件带缩进且含展示回放；这正是 §9.1 警告的
  "不能把文件缩进大小、JSON 字符数和数据库占用混为一谈"，报告里已分别列出。
- 浏览器 `estimate()` 在无头环境给出的 usage 明显滞后（0.17MB），**不能当作本应用账本**（§9.4 的原文要求）；
  报告里两者并列，且标注口径。


## 10. 工作纪律（本会话踩过的坑）

- **每改一处，跑 2~3 次再判定**（每次都是不同的随机牌局），并报告 `replayProgress` 与
  `kindMismatches` 的变化，不要只看 `replayOk` 的布尔值；
- 优先用 `analysis-probe.spec.ts` 迭代（25 秒一次），判定成立后再跑整条 `replay.spec.ts`；
- **先确认观测信号可信**：改完校验器先做新鲜度自检；诊断字段先确认来源；
- **提交门控**：先 `pnpm typecheck` + 相关测试通过，再 `git commit`；不要把失败的测试留在 master；
- **源文件与文档一律用编辑工具改**，不要用 PowerShell 文本改写（本会话 shell 文本处理三次造成损坏：
  源文件乱码、App.vue 乱码、交接文档被截断）；提交信息避免直引号，用「」；
- 改动在 master 提交后必须 `pnpm sync:vibehub`（要求 master 干净）；跑 e2e 需 dev server 在 4173 且
  `E2E_REUSE_ONLY=1`；
- 破坏性/推测性改动先跑 `powershell -File scripts/check-vibehub-ahead.ps1` 看审计。

其它历史教训：

- **断言静默跳过**：e2e 探针把 `checksum` 传空串导致解码全失败、条件为假、整段分析断言长期未执行
  —— 任何"容错分支"都不许把失败变成沉默；诊断输出必须放在可能失败的断言**之前**；
- **缺字段被静默默认值**：重建开局漏传 `dealer` ⇒ 它把真庄家的第 14 张下标从座位 0 的手里删掉；
  本次的 `openingScores` 是同一类（缺了就报错，不要默认）；
- **跨端 id 不能当标识**：窗口 id、peer id 之类跨端出现的值只能做展示，判等要用自增序号或事件 id；
  **同一实体的 id 也不能两处各生成一个**（§2.5 的场次 id 就是这么错的：分析区与牌谱各自 `createId()`，
  结果按 id 对账的回收逻辑把好数据整场删掉）；
- **记录顺序不等于执行顺序**：异步回传（机器人动作）会让条目顺序与引擎窗口顺序不一致，必须带可比较的位置判据；
- **单次运行不足以判定改动优劣**：随机牌局下必须 2~3 次复跑；
- **Windows 上不要用 PowerShell 文本改写源文件**（`Get-Content` 按 GBK 解码无 BOM 的 UTF-8 ⇒ 乱码）。

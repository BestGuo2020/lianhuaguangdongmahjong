> 其余部分（P0 全部、§3.3、§3.4、§5、§6 的数据层、§9.2–§9.5）均已落地并有单测/实测支撑，

## 2. 复现校验器的工作方式（`src/game/replay/analysis/replayReproduction.ts`）

1. `openingFromReproduction` 把记录还原成引擎开局（**缺任何必需字段都明确失败**，绝不用默认值顶替）；
2. 按记录顺序消费条目：命令 → 还原成当时的合法动作并提交；`expire` → 推时钟过截止时间再 `expire`；
   `auto` → 明确报"该窗口不是本端决定、记录不含其选择"；转场（`engine.transition`）→ 自行 `advance`（可推导，不需记录）；
3. 与记录的结束分数比对（有期望分时），否则只报"能跑完"。

## 3. 已确证的结论（都经过实验或实测）

1. **worker 回传生效**：`{kind:'bot'}` 把权威机器人实际提交的动作回传（`botAction`），真实录像里 `auto` 完全消失；
2. **`expire` 条目必需**：第 61 轮试过"下一条真命令能落当前窗口就跳过这条 expire" ⇒ 第 1 局从成功退回失败；
3. **两侧窗口 id 不可比**：记录 `round-1/window/39` vs 重放 `verify/1/window/42`；但**末尾编号单调**，可作相对位置判据；
4. **编号相对判定有效**：据此丢弃"属于已走过窗口"的 `expire` 后，偏移从 **+3/+5 降到 +1**；
5. **前置过滤（同窗口有命令则丢弃 expire）保留更好**：第 56 轮（单次运行）与第 72 轮（两次运行）两次停用实验都未改善；
6. **吃/杠必须按牌集合匹配**：这类动作不带单张 `tile`（用 `tiles/meld` 表达），只比 `kind` 会吃错组合；
7. **到点静默的座位原先不留任何条目**：`actBot` 在"到点或已不再等待"时提前返回 ⇒ 该座位在记录里凭空消失；现已补记 `expire`；
8. **可推导信息不要记录**：转场、`headDrawn` 等由引擎状态推出即可，记录它们只会引入不一致。

## 4. 当前未解决的问题

**重放比记录稳定多 1 个窗口**（实测 53/52、83/82），首个分叉处表现为：

```
记录期望：seat=N kind=win / kind=discard
重放当时：另一个窗口（如 turn[2] 或 win[1]），记录里属于该窗口的条目只有若干条 expire、没有任何命令
```

⇒ 类型判断：**"某座位的响应缺失"** —— 记录中某个窗口缺少应有的响应条目（或该条目未被重放消费），
使重放自行结束了该窗口，此后错开一位并累积。

## 5. 诊断工具（已在校验器里，失败信息会输出）

1. **窗口轨迹**：重放见过的窗口数 / 已消费记录涉及的窗口数（定位偏移量）；
2. **配对轨迹**：`记录条目 → 应用时重放所处的窗口（kind + 有合法动作的座位）`（定位断点位置）；
3. **缺失清单**：属于当前窗口编号的记录条目（判断"缺了谁的响应"）；
4. **expire 判定计数**：应用 / 编号更小丢弃 / 前置过滤丢弃（判断推进来源）。

## 5.5 方向修正（第 77~78 轮）

在"编号相对判定 + 同窗口去重"两条规则都就位后，测量结果变得非常整齐：

```
第 1 局：重放 80 / 记录 79      第 2 局：25 / 24
第 3 局：43 / 42                第 4 局：67 / 66      ⇒ 每局恰好 +1
```

而失败窗口的条目清单显示 **该窗口并不缺条目**（例如 `该窗口在记录中的条目=[1:discard]`）⇒
**分叉不是"条目缺失"，而是更早某个动作被应用得与当时不同**，导致手牌/副露不同，
于是该窗口里本应可用的动作不存在了。

据此，下一步不再查"条目归属/顺序"，改为**比对状态**。

## 5.6 下一步的具体做法（已具体化，可直接实施）

1. 让 `replayReproduction` 接受一个可选的**前态清单**：`states?: Array<{ windowId?: string; seat?: number; hand?: string[]; melds?: number }>`
   —— e2e 已经解码了全部分析记录，其中 `decisionState` 约 495 条、**自带该座位当时的手牌**（`hand` + `drawnTileIndex`），
   把 `tag === 'decisionState'` 的条目传进去即可（无需改动记录格式）；
2. 校验器在**每条命令应用之前**，取出该座位的手牌（`bloodFlowSeatView(engine, seat).hand`）与副露数，
   与对应前态比对；**第一处不一致即为状态分叉点**，直接输出：
   `第 N 条命令前：重放手牌=[…] vs 记录前态手牌=[…]`；
3. 有了这个分叉点，就能定位是"某条命令被执行成了不同的动作"（匹配器仍不精确）还是"某个窗口被多推进/少推进"（expire 语义）；
4. 仍然按 **2~3 次复跑**判定每一次改动（随机牌局）。


1. 用「缺失清单」把**所有**缺口成批列出（而不是逐个断点猜）：对每局、每个窗口编号，列出
   "记录中的条目"与"重放该窗口时等待的座位"，得到缺失清单；
2. 按缺失类型分别处理：
   - **录制侧未记**（例如某类窗口的某些座位主线程从不驱动）⇒ 在录制侧按 `expire`/`auto` 的既有语义补记；
   - **重放侧未消费**（条目存在但被判为过期/过滤掉）⇒ 修正判定条件（编号相对判据已有，可在此基础上收紧）；
3. 每改一处，**按 2~3 次复跑判定**（每次 e2e 都是不同的随机牌局，单次结果不足以判断优劣）；
4. `replayOk` 全 true 后，把 e2e 断言**收紧**为"真实录像必须全部复现成功"（当前允许"失败但原因确切"，会掩盖真实缺陷）；
5. 之后：`pnpm sync:vibehub`（多轮共享文件改动尚未同步）、§10 剩余条目（旧格式可读 / 导出包 / 单独删除分析区保留牌谱）、
   记录格式统一（牌码 vs 中文显示名）、P2P 路径的分析记录（需权威端参与，同 worker 回传那套）。

## 8. "先确认信号可信"——本项目踩过的四类元错误

排查 §10.6 时，真正拖慢进度的不是功能缺陷，而是**观测信号本身不可信**。以下四类都实际发生过：

1. **陈旧模块**：e2e 页面里跑的仍是旧版校验器（Vite 转换缓存），新加的诊断字段完全不出现，
   于是连续两轮在旧输出上做判断。**对策**：每次改完校验器先做"新鲜度自检"（例如断言某个新字段出现在输出里），
   需要时用受管后台作业重启 `pnpm dev -- --port 4173 --force` 并确认监听成功再跑。
2. **诊断读错字段**：读座位视图**顶层**的 `hand`（实际不存在）⇒ 恒为 0，产生过"该座位手牌 0 张"的假信号；
   正确位置是 `players[seat].hand`（本家可见，他人被遮蔽）。**对策**：诊断字段要先确认来源，再据其下结论。
3. **诊断与生产口径不一致**：诊断按"窗口编号"匹配、生产按"完整 windowId"匹配 ⇒ 结论分叉，看起来像 bug。
   **对策**：诊断与判定用同一口径；输出完整标识而不是截断后的部分。
4. **误判自己的判据**：曾以为 e2e 的 `replayOk` 偏弱（未传期望分数 ⇒ `scoresMatch` 为 null ⇒ `ok` 恒真），
   因而打算"补期望分"；重看断言后发现**组合断言已经有效**（ok ⇒ 无原因 + 消费完所有条目 + 结束分数与展示回放逐家一致）。
   **对策**：改判据之前先把现有一组断言读全，别只盯着单个字段。

另有一条与判据配套的纪律：**随机牌局下，任何"改好还是改坏"的判定都要 2~3 次复跑**；单次运行只够排除方向。

## 10. 主判据：每局复现进度（第 91 轮起）

`tmp/analysis-size.json` 里的 `replayProgress` 记录每局 `submitted/recorded`，量化"离跑完全部记录还差多少"，
并区分两类失败：**跑到终局但未消费完**（提前结束）与**中途卡住**（命令不匹配）。

**基线（实测，四个随机牌局）**：

```
replayOk       : false,false,false,false
replayProgress : 91/114   62/206   278/357   142/204      （约 80% / 30% / 78% / 70%）
```

四局均在 30%~80% 处因命令不匹配中止 ⇒ 分歧随对局推进累积。

**用法**：任何针对 §10.6 的改动都应报告它对 `replayProgress` 的影响（配合 2~3 次复跑），
不要只看 `replayOk` 的布尔值——后者会让"从 30% 推进到 80%"这类实质进步看起来毫无变化。

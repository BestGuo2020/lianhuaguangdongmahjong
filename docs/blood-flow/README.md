## 如何维护

1. 用户确定规则或体验边界后，更新 `rules.md`；未逐项确认的实现默认值仍明确标为默认值。
2. 开始或完成实现时，只更新 `tasks.md` 的状态；实现细则负责说明怎样做，不再放另一套进度表。
3. 验证后追加 `acceptance.md`：提交、命令、结果、证据位置和未验证范围。实现完成、自动化通过、视觉认可、实听通过分开记录。
4. 实验报告保留样本和提交。修改引擎后不改写旧数字冒充重测；重跑报告脚本会更新 `records/` 的对应报告，历史版本由 Git 保留。
5. 按仓库 [双分支工作流](../branch-sync-workflow.md) 提交和同步；未提交的并行改动不混入他人的交付。分支实时状态用 Git 核对。

旧的主实施、第二轮表现、验收及通用检查四个路径保留简短跳转，方便已有任务和链接找到新位置；不要再向旧路径追加正文。
